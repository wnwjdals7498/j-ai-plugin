# 03. 리뷰 기준

리뷰어는 작업 하나가 끝날 때마다 이 문서로 판정한다. 구현자도 커밋 전에 1절을 스스로 확인한다(00-discipline 5절 8번). 리뷰어는 코드를 고치지 않고 지적만 한다.

## 1. 공통 체크리스트

리뷰어는 각 항목을 **직접 확인한 근거**(명령 출력, 파일:줄)와 함께 통과·위반으로 적는다.

| # | 확인 | 방법 |
|---|---|---|
| 1 | 대상 파일 밖 변경 없음 | `git show --stat HEAD`와 작업의 "대상 파일" 비교 |
| 2 | 수용 테스트 표의 모든 행에 테스트가 있음 | 테스트 함수 이름 `test_<작업ID>_<행>_…`로 행 번호 대조 |
| 3 | 테스트 약화 없음 | 이전 커밋 대비 테스트 삭제·단정 완화·`skip`·`xfail` 추가 여부(`git diff HEAD~1 -- tests/`). `skip`은 C-27의 두 경우만 |
| 4 | 전체 테스트 통과 | 리뷰어가 직접 `cd docdb && .venv/bin/python -m pytest` 실행 |
| 5 | 새 공개 이름이 모두 계약에 있음 | 새로 생긴 `def`(밑줄로 시작하지 않는 것)·명령·오류 코드·출력 줄을 C-xx와 대조 |
| 6 | import 규칙 | `tests/unit/test_import_guard.py` 통과, 새 import 줄 확인 |
| 7 | Python 3.11+ 기능 없음 | C-02 목록을 grep(`tomllib`, `ExceptionGroup`, `except*`, `typing.Self`, `datetime.UTC`, `StrEnum`, `TaskGroup`, `LiteralString`) |
| 8 | 쓰기 경로 | 쓰기가 `write_tx` 안, `RECORDED_TABLES` 쓰기마다 `append_change`, 자유 텍스트에 `normalize_text`·`assert_no_secrets` |
| 9 | SQL 매개변수화 | f-string·`%`·`+`로 값을 넣은 SQL 없음 |
| 10 | 출력 형식 | 계약에 적힌 문자열과 한 글자씩 같음(공백·구분자 포함) |
| 11 | 오류 처리 | `DocdbError`와 C-05 코드만, 빈 `except`·`except Exception: pass` 없음, 비밀 값·본문이 `detail`에 없음 |
| 12 | 시간 | `datetime.now` 직접 호출 없음 |
| 13 | stdout | MCP 경로에 `print` 없음 |
| 14 | 금지 영역 | 커밋된 마이그레이션, `docs-db/reference/`, `docs-db` 결정 문서 변경 없음 |
| 15 | 커밋 | 메시지 형식(00-discipline 9절), 작업 하나만 포함 |
| 16 | 범위 | 작업 범위 밖 기능을 미리 만들지 않음(계약에 있어도 다른 작업 몫이면 위반) |

## 2. 작업별 중점 확인

| 작업 | 중점 |
|---|---|
| T02 | `canonical_json`의 구분자·정렬, `tok_est` 올림, `q` 규칙이 원본과 같은지 |
| T04 | `write_tx`의 중첩 SAVEPOINT 이름이 깊이별로 다른지, 예외가 다시 던져지는지 |
| T05·T06 | 0001·0002가 원본과 바이트까지 같은지(sha256), 마이그레이션 SQL에 `BEGIN`·`COMMIT`·`user_version`이 없는지, 0007 트리거가 C-10 정규식과 같은 경우를 거르는지 |
| T07 | `row_digest` 공식의 키 이름(`t`, `e`, `seq`, `op`, `after`, `prev`) |
| T10 | 시작 카탈로그의 `[설계 판단]` 표시, 시드 39행 원본 일치 |
| T12 | 원본과 출력이 같은지(이식 테스트 28건), 원본에서 바꾼 부분이 9가지 목록 안에 있는지 |
| T16 | 같은 입력에 같은 결과(R2·R3 재계산이 불필요한 이력을 만들지 않는지), 규칙이 사람의 반려를 뒤집지 않는지 |
| T21·T22 | 오프셋이 원본 바이트 기준인지, 코드 블록 처리, 한 번의 `label`이 전부 아니면 전무인지 |
| T24 | 파일 전체가 Python 3.6 문법으로 파싱되는지(`/usr/bin/python3.6 -m py_compile`) |
| T25 | stdout 오염 없음, `docdb_put` 설명 문자열 정확 |
| T26 | `claude plugin validate` 결과 원문, JSON 버전 일치 |

## 3. 판정과 보고 형식

```text
작업: T<번호>
판정: 통과 | 수정 필요 | 멈춤
근거: 1절 각 항목 통과·위반 + 확인 명령 출력 요약
지적(수정 필요일 때): 
  - <파일:줄> 위반 <1절 번호 또는 계약 C-xx> — <무엇이 틀렸나> → <수정 방향>
멈춤 사유(계약·작업 문서 자체의 문제일 때): 00-discipline 7절의 6항목
```

- **수정 필요**: 오케스트레이터가 같은 구현자에게 지적을 전달한다. 수정은 최대 2회. 그래도 통과하지 못하면 오케스트레이터가 사용자에게 보고한다.
- **멈춤**: 계약·작업 문서가 모순되거나 빠진 경우. 오케스트레이터가 문서를 고친 뒤 작업을 다시 배정한다.

## 4. Review Focus — 테스트로 묶어 둔 고위험 입력

명세가 직접 말하지 않지만 사용자가 실제로 만날 가능성이 높은 입력과 그것을 붙잡는 테스트다. 리뷰어는 해당 작업에서 이 테스트가 있고 약화되지 않았는지 확인한다.

| # | 입력·상황 | 기대 동작 | 붙잡는 테스트 |
|---|---|---|---|
| 1 | Windows 줄바꿈(CRLF), macOS 파일명 분해형(NFD) | 같은 내용은 같은 digest, 불필요한 `CONFLICT`·`STALE` 없음 | T02 #4·#5·#7, T12 #29, T21 #3 |
| 2 | Claude와 Codex가 같은 프로젝트 DB에 동시에 쓰기 | 잠금 오류 없이 대기 후 성공, ID 중복 없음 | T04 #9, T08 #8 |
| 3 | 에이전트가 토큰·키를 본문에 넣음 | 저장 거부, 오류에 비밀 값 미노출 | T09 #11, T12 #30, T14 #7, T20 #7, T23 #5 |
| 4 | 플러그인 갱신 후 오래된 DB, 또는 더 새 플러그인이 만든 DB | 명확한 오류(종료 코드 3), 마이그레이션 실패 시 원상 복구 | T05 #5~#8, T11 #8·#9 |
| 5 | 이상한 import 입력(코드 블록 속 `#`, BOM, UTF-8 아님, 제목 없음, scan 뒤 원본 수정) | 올바른 분할, 지원 안 함 보고, 변경 감지 후 전부 취소 | T21 #1~#6, T22 #8 |

추가: DB가 없는 폴더에서 MCP 서버가 죽지 않고 안내 문자열을 반환(T25 #3).

## 5. 전체 브랜치 리뷰 (마지막)

T26까지 끝나면 가장 성능이 높은 모델의 새 리뷰어가 브랜치 전체를 본다.

| 확인 | 방법 |
|---|---|
| 계약 전 절(C-01~C-27)에 구현 작업과 테스트가 있음 | 절마다 구현 파일·테스트 파일 대응표 작성 |
| 결정 D1~D27이 코드에 반영됨 | 결정마다 근거 위치(파일:줄) |
| 죽은 코드·쓰이지 않는 공개 함수 없음 | grep으로 호출처 확인 |
| 문서와 코드 불일치 | 12-features 상태 열, 11-schema 7절과 실제 마이그레이션 비교 |
| Review Focus 5건 테스트 존재·통과 | 4절 표 대조 |
