# Authenticated storage with local execution

Connect with `pmt connect --handoff <file> --credential-file <file>` or Claude /plugin handoff_file plus sensitive device_credential. Then select the handed-off project with `pmt link <name>` and run `pmt check`. Stored credentials are OS-protected and never written to the Hook environment file. Keep TLS verification; compare the public CA fingerprint separately. Host setup and device issuance use the separate pmt-server administrator skill.

An existing local profile needs explicit `pmt storage switch`; entering Host settings alone preserves local. Switch rejects unresolved pending or active claims and keeps the local DB. `pmt disconnect` removes only the stored token. Same-root products share one identity; use separate ConfigRoots for separate devices.

Use the installed `pmt` and its selected ConfigRoot/DataRoot. `pmt storage status` reads the local profile; `probe` verifies the actual connection. `configure` accepts one JSON object with `mode`, `expected_config_sha256`, and for hosted mode endpoint, credential environment-variable name, registered device/namespace, optional CA and explicit workspace mappings. It probes before publishing the config. Secret values are never part of that JSON. Do not run ordinary local `setup` against a hosted profile or change user settings for a test.

Host owns the selected namespace's SQLite execution state, Queue, scopes, resource references and replay records. A connection failure is an error; do not open a local business database as a fallback. Model selection, native tools, local CLI processes, Git, document files and process configuration remain client operations. Execution identity/selection metadata may cross the wire; commands, environment variables, PID, credentials and spool paths may not.

Before reading task contents, acquire the current run's scopes and require successful ownership. Resolve repository/project/branch to the configured local checkout only after authenticated Host authorization. Inspect actual local source, containment, links and Git identity; compare its SourcePin with the current Host source. Another local path does not make the same repository/branch/file an independent scope.

Publish a source as an immutable `graph_snapshot` resource plus `publish_source_snapshot` CAS pointer. A client snapshot records provenance; Host has not executed Git to prove it. Verification snapshots similarly come from the actual client target before/after inventory and scoped evidence. Never substitute Host's runtime or a caller Boolean for the target's conditions.

For `capture_work_basis`, use the hosted client adapter. It first obtains Host authorization for the current run, scope locks and explicit workspace mapping, then reads Git and selected file hashes on that client. It repeats the source and inventory observations before publishing. Host checks the live run/source snapshot and builds the SQL work/revision section itself. The stored source is marked `client_attested` and `host_git_verified=false`. Only hashes, counts and retained refs cross this boundary; relative path/hash detail stays in the owner-scoped client spool. If the source snapshot, run revision or owner changed, capture must stop and be repeated from current state.

For a new hosted project's implementation Steps, complete both trees and the F4 document baseline first. Call `publish_client_plan` as an explicit review action with the current SourcePin/run, complete document-effect ID/revision, requirements/plan versions and new plan UUID (expected prior plan hash null). It validates the actual graph and registered coverage and publishes only plan metadata referencing the existing resource. `read_client_plan` returns its version/hash/refs. A draft or outdated source is not an implementation plan.

Routing policy/capability operations stay in the client's ConfigRoot `routing-client.sqlite3`; they do not open the local business database or send policy/provider configuration to Host. Existing preferences can be imported read-only, while old capability observations become unknown and need fresh observation. `select_execution_route` applies the same Phase 2 rules. Pass only `route_for_enqueue(selection)` to Host `enqueue_execution`, preserving the selected identity and verified capability reference. Selection metadata does not grant scope or permission; actual execution still checks the current Host plan, Step, source and ownership.

Use current F5 context and F6 reuse references for `advance_execution_control`. Keep the exact request ID, source, nonce, control/run revisions and returned bounded native action. The main session calls the native tool once and ACKs its actual opaque handle. Same nonce/handle replay may recover a lost ACK; a different handle is a conflict. Prompt text belongs only to the private original response, not shared metadata or general logs.

For a prepared F9 group, read the current batch and every child's authorized context. One physical handle serves the explicit ordered logical members. Keep each child's criteria and result separate. Missing results, unconfirmed stop or unreviewed siblings retain the scope union. Process completion and model success are not independent test passes or Done.

If Host stops while an already-attached local process runs, preserve its managed spool. `HostedLocalRuntime.capture_terminal_receipt_offline` may inspect only that existing owner-bound dispatch and actual terminal receipt/output hashes. It does not authorize new working-tree reads, execution, shared writes or claim recovery. `PendingOutbox` preserves already-generated resource bytes and completed results, scoped to namespace/actor/device/environment/session. Publish the original resource upload before constructing the immutable final request when its ref is not yet known.

Use `pmt pending capture` offline with existing `session_id`, `scope_id`, `run_id`, `context_ref`, `source_hash`, and `dispatch_ref`; it returns staged resource refs/hashes. `pmt pending status` takes the existing session ID and lists only that owner's result/resource metadata. `pmt pending reconcile` uses the same refs and optional original `pending_request_id`, verifies the online Host, publishes the staged bytes, and reconciles one immutable result request. Each command accepts one JSON object and returns the normal CLI envelope. A new command request ID does not replace the original resource/result effect IDs.

After reconnect, obtain actual authenticated compatibility, current source/F5/run and owner/scope facts. Query the original request ID with its semantic fingerprint first. A committed result is recovered without another write; an absent result is replayed only with the exact original body/ID and current allowed state. Stale/conflict/unknown stays visible. Do not change the body/ID, unlock, merge or relaunch to make it succeed.

Migration uses a quiescent version-pinned manifest, sanitized SQLite and hash-checked resource set into a verified empty namespace. Original data and target device authentication remain separate. A backup/restore receipt is not an automatic primary switch. Fixture HTTPS/process evidence does not prove production Linux, remote deployment, real model quality or provider token savings.
