# PMT 작업 규칙

이 폴더의 목표는 로컬 PMT 구현 → 본체 동작 검증 → 플러그인화 → 설치 검증을 1단계로 완성하는 것이다. 최신 상세계획은 [1단계 작업 안내](docs/phase1/README.md)다. 문서의 계획·예정 시험을 구현 완료·실측 성공으로 표현하지 않는다.

## 착수 전에 읽을 것

1. [단계·의존성·작업 배정](docs/phase1/README.md).
2. [공통 입력·출력·상태 계약](docs/phase1/contracts.md).
3. [배정받은 작업 묶음](docs/phase1/work-packages.md)의 해당 항목.
4. 그 항목의 [시험 ID](docs/phase1/verification.md)와 [로그 규약](docs/phase1/logging.md).
5. 연결부·배포 작업이면 [제품·패키징 규약](docs/phase1/adapters-packaging.md).

전체 자료를 반복 통독하지 않고 배정 범위·의존 계약·관련 근거를 읽는다. 서로 다른 규약을 발견하면 상세 공통 계약을 기준으로 차이를 메인에게 보고한다. 사용자 지시가 문서보다 우선한다.

## 병렬 작업

- 메인은 범위·공통 계약·기술 결정·통합·최종 검증을 책임진다. 구현 작업자는 사용자가 지정한 `gpt-6-luna`를 사용한다.
- 같은 코딩 에이전트에서 대상 모델·도구·권한을 지원하면 네이티브 서브에이전트를 우선한다. 지원하지 않는 모델을 임의로 대체하지 않는다. 명시된 다른 실행 경로는 사용자 선택을 따른다.
- 기본 동시 작업은 3개다. 실제 실행기 한도 내에서, 독립 작업만 병렬로 배정한다. 의존 작업은 승인된 계약·검증 결과를 받은 뒤 시작한다.
- 작업자는 한 묶음의 소유자다. 착수 시 수정할 영역·예상 산출물·공유 경계를 메인에게 알리고 다른 소유 영역을 수정하지 않는다. 공유 파일이 생기면 메인이 소유자를 지정한다.
- 공통 데이터·명령·상태·오류·로그 계약과 스키마 변경은 메인이 결정한다. 변경 이유·호환성 영향·연관 시험을 제안하고 확정 전에는 소비자가 임의로 맞추지 않는다.
- 하위 작업자는 자신의 결과와 증거를 반환한다. 전체 완료 판정, 사용자 데이터의 PMT 최종 상태 반영, Git 통합·커밋·푸시는 메인이 맡는다.
- 같은 파일·작업 공간을 동시에 수정하지 않는다. 필요한 경우 작업별 worktree를 사용하고 통합·공유 상태 변경은 직렬화한다.
- 모호함이 자기 범위 안의 구현 선택이면 근거를 기록해 해결한다. 공통 계약·사용자 결정·운영 범위를 바꾸는 문제면 메인에게 보고한다.

## 구현 규칙

- 목적·이유·입출력·관계·완료 기준을 충족한다. 작업 계획을 특정 파일의 줄 단위 수정 목록으로 바꾸지 않는다.
- 런타임은 Python 표준 라이브러리와 SQLite를 우선한다. 필요한 새 의존성은 목적·대안·설치·업데이트 영향을 메인에게 제시한다.
- 제품별 연결부·CLI·스킬은 공통 PMT를 호출한다. DB 접근과 상태 판정을 복제하지 않는다.
- 상태·revision·업무 이력·성공 요청의 재처리 기록은 같은 DB 트랜잭션으로 저장한다. 파일 저장의 원자성은 별도 계약을 따른다.
- `request_id`는 호출 재전송, `event_id`는 원 이벤트 식별자다. 원문 내용이 같다는 이유만으로 두 사용자 행동을 합치지 않는다.
- 시간 경과·응답 종료·idle만으로 점유 회수 또는 Done 전이를 하지 않는다. 명시적 착수·해제·완료와 근거를 사용한다.
- 플러그인 코드와 사용자 DB·리소스 경로는 분리한다. 테스트에는 격리된 데이터만 사용한다. 실제 사용자 설정·DB를 설치 시험용으로 덮어쓰지 않는다.
- 정보성 근거는 공식 문서·원본 코드·재현 가능한 시험만 사용한다. 출처를 읽고 확인한 내용과 설계 선택·미확인 사항을 구분한다.
- 실패 원인·해결 원리·수정 방법은 로그·공식 근거·테스트 결과로 입증한다. 실서비스 문제는 허용된 범위의 복구를 우선하고 원인·재발 방지 작업을 이어간다.

## 검증·로깅

- 변경한 계약의 필수 시험을 수행하고 명령·실제 종료 코드·대상 상태·환경·증거를 남긴다. 코드가 존재하거나 모델이 성공을 말한 것만으로 완료하지 않는다.
- DB 동시성은 독립 프로세스와 실제 DB로 검증한다. 훅 fixture 시험, 본체 시험, 실제 제품·설치 시험을 구분한다.
- 실패·미실행·실행 차단·이후 무효가 된 성공을 구분한다. 제품 미설치·권한 부족은 해당 제품 시험의 `blocked`이며 통과로 바꾸지 않는다.
- 같은 대상·환경·입력·검증 정의·근거가 유효하면 기존 결과를 재사용한다. 차이·실행 중 변경·증거 누락·이후 실패가 있으면 관련 시험을 다시 실행한다.
- 업무 이력·진단 로그·검증 증거를 분리한다. 로그에 비밀키·토큰·전체 대화·환경 변수 전체를 넣지 않는다. CLI stdout은 계약 JSON 전용이다.
- 로그 실패를 숨기지 않는다. 진단 로그 실패와 업무 이력 저장 실패의 처리 차이는 공통 계약을 따른다.
- 플러그인화 이후 격리된 설치·업데이트·제거 후 재설치·실제 훅·새 세션 재개를 확인해야 1단계가 완료된다.

## 작업 지시·인계 형식

메인의 지시에는 작업 ID, 목표·이유, 범위·연관 부분, 입력·출력 계약, 선행 작업, 기술·근거, 필수 시험 ID, 로그·증거, 제외 범위, 완료 기준을 넣는다. 파일별 수정 지시는 요구하지 않는다.

작업자의 보고에는 작업 ID, 결과 요약, 실제 변경 영역, 계약 변경 제안, 수행 시험·종료 코드·증거, 대상 commit·dirty 상태, 미해결·다음 조치, 연관 작업에 전달할 내용을 넣는다. 최종 인계 규격은 [작업 안내](docs/phase1/README.md#작업-지시와-인계)에 따른다.
