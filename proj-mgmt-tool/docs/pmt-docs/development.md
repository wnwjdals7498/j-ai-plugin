# 구현·배정·검증 규칙

## 코드 규칙

- 공개 경계의 입력·출력 의미, 타입·제약·실패를 먼저 확정한다. 외부 입력은 경계에서 검증하고 업무 규칙은 공통 서비스에서 한 번만 적용한다.
- 모듈의 책임을 좁게 유지한다. 시간·외부 프로세스·모델 호출은 교체 가능한 경계로 두되 실제 사용 없는 범용 추상화는 만들지 않는다.
- SQLite 상태·revision·업무 이벤트·성공 재처리 결과는 같은 트랜잭션으로 저장한다. SQL은 매개변수를 바인딩한다. 파일은 staging·hash·게시·참조 계약을 별도로 따른다.
- 요청 재전송은 같은 request ID와 같은 의미 입력으로 처리한다. 같은 ID의 다른 입력은 충돌이며 내용이 같다는 이유로 별개 사용자 행동을 합치지 않는다.
- 오류는 입력/충돌/일시장애/내부오류로 구분한다. 실패를 성공값으로 삼키지 않고 재시도 가능 여부를 근거로 지정한다.
- 새 의존성은 목적·공식 근거·대안·설치/업데이트·호환성·시험 영향을 메인이 확인한다. 코드·설명·시험의 상태를 함께 갱신한다.
- 본체·DB·리소스·사용자 설정은 배포물과 분리한다. 격리된 시험 root만 사용하고 사용자 환경을 시험 때문에 덮어쓰지 않는다.

## Step 인계 계약

| 지시할 내용 | 필요한 의미 |
|---|---|
| 목적·goal·non-goal | 작업 이유, 관찰 가능한 성공, 제외 목표 |
| 근거·부모 | 대전제, 두 트리 노드, Item, 제품 단계, 결정·검증 참조 |
| 범위·자율성 | 추가/수정/삭제할 기능·모듈 경계, 공유/금지 범위, 독자 판단 한도 |
| input/output | 각 값의 의미·타입·제약·불변식·실패 의미; 비밀/운영 실값 제외 |
| 방법·기술·의존성 | 선택 원리·근거, 선행 산출물, 도구·환경·권한 |
| 시험·로그 | 수용 기준, 시험 ID, 관찰 지점, 증거·재사용 조건 |
| 버전·완료 | 요구/계획/지시 버전, 결과 형식, 검토자·완료 조건 |

지시를 “어느 파일 어느 줄을 수정”하는 목록으로 분해하지 않는다. 작업자는 착수 시 실제 변경 영역을 제안해 점유 경계를 확인한다. 반환에는 실제 변경 범위, 기준별 결과, 명령·종료 코드·증거, commit/dirty 상태, 잔여 문제·연관 작업 전달 사항을 포함한다.

## 병렬 구현 묶음 — 2단계

구현 지시의 목적·변경 범위·goal/non-goal·입출력·기술·Test·로깅·완료 기준은 [Q0~Q9 상세계획](../phase2/README.md)을 따른다. 아래 표는 구조상 책임 요약이다.

| 묶음 | 목적·입력 → 출력 | 선행·소유 경계 |
|---|---|---|
| 공통 계약·이관 | 확정 요구·현재 schema → Step/Queue/runner/로그 계약·이관안 | 메인 소유; 소비자가 먼저 다른 규약을 만들지 않음 |
| 계획·graph | 요구·결정·자원 → 두 트리·명세·문서/graph·validator | 공통 계약 뒤 독립 개발; planning 소유 |
| 경로·runner | capability·실행 지시 → 실제 경로·handle·정규 결과 | 공통 계약 뒤 독립 개발; routing/runners 소유 |
| Queue·범위 점유 | Step·실행 요청 → 안전한 실행/대기·결과·복구 | 공통 계약 뒤 독립 개발; execution/저장 변경 소유자 지정 |
| Git·근거 연계 | 기준 commit·변경·문서 → 갱신·영향·무효화 | graph/점유 계약 후 개발; reconciliation 소유 |
| 통합·제품 검증 | 위 산출물 → 실제 제품별 실행·회귀·완료 기록 | 메인 통합; 사용자 지시 모델의 작업자와 검증 범위 분담 |

구현 작업자는 `gpt-6-luna`, 기본 독립 병렬 작업은 3개다. 같은 공유 파일·스키마를 복수 작업자가 수정하지 않는다. 별도 worktree도 계약 충돌을 해결해 주지는 않으므로 통합은 직렬화한다. 메인이 최종 검증·PMT 완료·Git 커밋/푸시를 맡는다.

## 필수 시험과 증거

아래는 **예정 수용 시험 ID**다. 실행 기록이 생기기 전에는 통과로 표시하지 않는다. 1단계 기존 시험 ID는 [기존 검증 계획](../phase1/verification.md)을 유지한다.

| ID | 입력·시나리오 | 기대 결과·관찰 |
|---|---|---|
| P2-TREE | 두 트리 종료/위임, 누락 참조·순환·대전제 변경 | 문서/graph 추적·검증, 영향 가지 무효화만 발생 |
| P2-ROUTE | 기본 절약형·사용자 지정·native 지원/미지원·API 금지 | 실제 모델/경로·선택 이유 일치, 불가 경로 blocked |
| P2-LOCK | 독립 프로세스가 동일/겹치는/독립 범위·다중 범위 요청 | 충돌은 하나만 성공, 독립 병렬 허용, 부분 점유/교착 없음 |
| P2-RUN | 정상·실패·중복 결과·실행 시작 전후 강제 종료 | 재시도 한도·중복 방지·reconciling·결과 복구 |
| P2-CANCEL | 종료 전/후 취소, 미응답 runner, 메인 세션 종료 | 취소 확인 전 완료/해제 없음, 다음 세션에서 결과 회수 |
| P2-GIT | 미확인/동일 commit·비진행·dirty·브랜치 변경 | 지정 시점 갱신·영향 반영, 기존 변경 보존 |
| P2-DATA | schema 2 이관·백업 복원·stale 지시·후속 실패 | 관계 보존, 오래된 실행/검증 거부, Step/Item/Work 판정 분리 |
| P2-OBS | 정상·지연·쓰기 실패·민감 입력·정리 대상 | 진행/로그 연결, 비밀·지시 원문 미노출, 참조 자료 보존 |
| P2-NATIVE | Codex/Claude/OpenCode의 실제 설치·세션·실행 경로 | 실제 지원 경로마다 배정/결과/취소·재개 확인 |

단위 시험은 순수 규칙, 통합 시험은 실제 임시 SQLite·파일·독립 프로세스, 제품 시험은 실제 제품의 호출 경계를 확인한다. fixture·가짜 모델 응답은 통신 검증이며 실제 모델 능력/품질 확인과 구별한다. 미설치·인증/권한 부족은 `blocked`, 실행하지 않은 것은 `not_run`이다.

현재 상태·입력·검증 정의·환경·근거가 일치하면 유효한 결과를 재사용한다. 변경된 계약의 필수 시험과 관련 회귀부터 수행하고 영향 없는 전체 시험을 반복하지 않는다. **2단계 완료는 정의된 전체 기능·제품 연결의 구현과 시험 완료**이며 일부 prototype만으로 판정하지 않는다. 미해결 blocked가 있으면 완료 조건의 미충족으로 보고한다.
