# 2단계 통합 작업 계획: Q7–Q9

이 문서는 Git·관찰/보존·제품 통합 작업의 상세 계획이다. 모두 예정 작업이며 구현 또는 시험 성공을 뜻하지 않는다. 공통 인터페이스·스키마·event 필드의 최종 이름과 의미는 메인이 확정한다.

## 공통 인계 기준

- 세 묶음은 요구 버전, 계획 버전, 기준 Git commit, dirty 지문, 실행 ID, 시험 정의 버전으로 서로 연결한다.
- 입력값은 ID·버전·참조·지문 같은 식별 의미로 기술한다. 운영 경로, commit, 설정, 사용자 데이터 등 실값은 계획 문서에 넣지 않는다.
- 출력은 판정, 영향 범위, 안전한 참조, 상태, 근거 manifest다. 원문 지시·대화·비밀은 결과나 로그에 복제하지 않는다.
- DB 상태·revision·업무 이력·성공 재처리 응답은 한 SQLite 트랜잭션에 둔다. 파일 게시·해시는 별도 단계이며 파일과 DB의 원자성을 가정하지 않는다.
- 검증 재사용은 대상·환경·입력·검증 정의·필수 근거가 같고 이후 무효화 사유가 없을 때만 허용한다.
- 오래된 계획·지시 버전의 결과는 현행 상태를 완료시키지 않는다. 늦게 도착한 결과는 보존·연결하고 적용 가능성을 재검토한다.
- 작업 지시를 파일별 수정 절차로 만들지 않는다. 완료 보고에는 실제 변경한 파일/영역을 기록한다. 작업자는 착수 시 변경 영역을 제안하고 실제 영역·증거·dirty 상태를 인계한다.

## Q7 — Git 최신화·대전제 영향·검증 재사용

### 목적과 범위

Q7은 Git의 대전제·구조·결정·graph 최신본을 SQLite 업무 실행과 안전하게 연결한다. 계획·Step의 근거 기준을 고정하고 변경 영향을 필요한 가지와 증거에만 전달한다.
추가 범위: 점유와 상태를 고려한 commit 탐지·분석, 기준 ref/hash 갱신, 변경 영향 연결, dirty 변경 보호, stale 결과 거부, 유효 검증 재사용 판정, 파일/DB 불일치 journal 및 재기동 복구 절차.
수정 범위: 기존 기준 commit·문서 참조·graph version 저장 의미를 실행 기준으로 보완하고, Git 검토와 실행 전 승인 순서를 명시한다. 검증 manifest의 commit·dirty fingerprint 연결을 사용한다.
삭제 범위: 단순 SHA 교체만으로 최신화 완료 처리하는 규칙과, 문서 본문·graph를 DB에 복제해 따로 편집하는 흐름을 제거한다.
Goal: 각 실행이 검토한 기준을 재현할 수 있고, 변경 시 영향을 받은 계획·증거만 무효화하거나 재검토 대기시킨다.
Non-goal: 사용자 dirty 변경 자동 저장·덮어쓰기, 자동 rebase/merge/commit, Git 이력 재작성, 전 작업의 일괄 무효화, Git 없는 저장소에 Git을 강제하는 일.

### 입출력 의미와 순서

입력은 작업 상태·범위 lock 획득 결과, 선택된 기준 브랜치/ref, 마지막 검토 commit, 미확인 commit 범위, dirty 상태 지문과 owner, 현재 문서·graph·계획·지시 버전이다.
출력은 검토 commit, 변경 요약의 안전한 참조, 영향 노드·Step, 기준 갱신 판정, 무효화/재검토 대상, 충돌·복구 상태 및 검증 재사용 적격성이다.
진행 중 작업은 점유 범위를 확보한 뒤, 미확인 commit이 있을 때만 그 commit들을 분석한다. 이미 검토한 commit을 반복 적용하지 않는다.
비진행 작업은 실행 시작 직전에 기준을 최신화한다. 작업 범위 lock을 얻고, Git 차이를 판별한 후에만 관련 상세 문서·graph·지시를 읽는다.
진행 중의 새 미확인 commit도 lock 뒤 제한된 변경 범위를 분석한다. 기준을 바꾸면 영향 작업을 중지·재계획하고 새 지시 버전을 고정한다.
미커밋 변경은 별도 지문·owner·관찰 시점으로 기록한다. 자동 덮어쓰기나 기준 commit에 포함하지 않으며 충돌은 소유자 조정으로 돌린다.
브랜치 전환·이력 단절은 기존 비교 기준을 그대로 재사용하지 않고 기준 재설정 검토를 요구한다. Git 없는 프로젝트는 문서/대상 지문을 기준으로 남긴다.

### 기술 선택과 이유

프로젝트 문서 원본은 Git에 둔다. SQLite에는 검토 기준과 참조만 저장해 중복 본문이 서로 달라지는 문제를 막는다.
commit 분석과 영향 판정은 읽기 전용 입력으로 시작하고, 승인된 기준 참조 변경만 짧은 DB 트랜잭션으로 기록한다. 모델 실행 중 DB 쓰기 잠금을 잡지 않는다.
파일·DB 사이에는 recovery journal 또는 동등한 복구 표식을 둔다. 임시 계산→파일/참조 게시→DB 상태 기록의 각 경계를 식별하고 재시작 시 완료·보상·수동조치 필요를 구분한다.
한쪽 게시 뒤 다른 쪽 저장이 실패하면 성공 응답을 하지 않는다. 재시도는 기존 request/event/run 식별자와 결과를 조회해 중복 실행을 피한다.
backup/migration은 DB와 리소스 manifest의 연결을 보존한다. 복원 전후 manifest hash·참조 hash를 비교하고 별도 빈 root에서 검증한다. 불일치면 증거를 재사용하지 않는다.
stale version 반환은 최신 Step 완료·Item 충족·Work 통합 판정에 반영하지 않는다. 원 실행·응답은 감사 참조로 보존하고, 최신 지시로 재실행하거나 상위 재검토를 받는다.
검증 결과는 같은 정의·commit 및 dirty 지문·환경·입력·증거가 유효하면 재사용한다. 영향을 받지 않은 증거는 보존한다. 후속 실패·증거 손상·요구 변경은 관련 자격을 만료한다.

### 선행·연관과 시험

선행은 메인의 기준 정보·revision·지시 버전 계약, 범위 lock, graph 노드 참조, 시험 manifest 의미 확정이다. Q7은 공통 필드 이름을 독자 결정하지 않는다.
연관 묶음은 Queue/runner, graph 작성, schema 2 이관·복원, 검증 evidence 저장이다. Q8의 추적 로그와 manifest 지문을 공유한다.

**P2-GIT-01** 동일 commit 재조회는 변경 분석·업무 갱신을 중복하지 않고 같은 검토 근거를 돌려준다.
**P2-GIT-02** 진행 중 작업은 미확인 commit만 분석하고, lock 전 상세 내용 read를 하지 않는다.
**P2-GIT-03** 비진행 작업은 시작 직전 최신화한 뒤 기준을 고정하고 실행한다.
**P2-GIT-04** dirty 변경은 owner와 지문을 보존하며 commit·덮어쓰지 않고 충돌 조정 상태를 반환한다.
**P2-GIT-05** 대전제 변경은 영향 가지와 Step을 식별·정지·재계획시키되 무관한 가지와 증거는 유지한다.
**P2-GIT-06** 브랜치 이동·이력 단절·Git 부재를 기존 기준으로 오판하지 않는다.
**P2-DATA-11** SQLite commit 전후 프로세스 종료를 주입해 journal/recovery가 고아 파일·누락 참조·중복 업무를 구분한다.
**P2-DATA-12** backup/migration/restore는 참조 관계 및 hash를 보존하며 불일치 증거를 재사용 불가로 만든다.
**P2-DATA-13** 오래된 지시·요구 버전 결과와 늦은 callback은 현재 완료 판정을 바꾸지 않는다.
**P2-DATA-14** 동일한 유효 시험은 재사용하고 입력·환경·정의·근거 변경 또는 후속 실패는 재검증한다.

### 관찰·완료 인계

제안 관찰 event는 `git.sync.started`, `git.commit.reviewed`, `git.baseline.updated`, `plan.impact.detected`, `evidence.reuse.decided`, `recovery.reconciled`다. 메인이 event 표기와 필드 계약을 통합한다.
추적 필드 의미: correlation/request/run, Work·Item·Step, 이전/새 기준 ref 및 검토 commit, dirty fingerprint/owner 참조, 영향 노드 수·참조, 계획·지시 버전, 재사용 판정 이유, transaction outcome, journal 상태.
Q7 완료 인계는 입력 지문·기준·dirty 상태·영향 결과·재사용/무효화 근거, 실행한 시험 ID/명령/종료 코드/증거, 실제 변경 영역과 남은 복구 위험을 포함한다. 메인이 전체 영향 해석을 확인한다.
자율 보고 경계: 안전한 변경 요약·참조·충돌은 작업자 자율 보고. 대전제의 사용자 목표 충돌, dirty 소유 불명, 불가역 복구, 공통 계약 변경은 메인에게 즉시 보고하고 판정 전 진행을 보류한다.

## Q8 — 진행 관찰·로깅·보존·정리·진단

### 목적과 범위

Q8은 장기 작업의 실제 상태와 마지막 변화 시점을 드러내고, 장애 진단에 필요한 로그·업무 이력·검증 증거를 분리해 안전하게 보존한다.
추가 범위: run 관찰 snapshot, 상태별 진행 UI/조회, 파일 진단 로그 회전·보존, 참조 확인 후 임시자료 정리, 백업·복구 상태 진단, 비밀 정제와 쓰기 실패 처리.
수정 범위: 공통 diagnostics 허용 필드 로거를 2단계 correlation·Work/Item/Step/job/run 참조에 연결한다. 기존 stderr JSONL은 유지 기준으로 사용한다.
삭제 범위: 근거 없는 진행률, 마지막 변화 시간을 매 heartbeat마다 갱신하는 표시, 참조 여부를 확인하지 않는 임시 파일 삭제 규칙을 없앤다.
Goal: 60초 이내 관찰 가능한 상태를 제공하며, 관찰 실패·진단 실패·업무 실패를 혼동하지 않는다. 참조 증거는 보존된다.
Non-goal: 전체 대화·지시 본문 저장, 진단 로그를 업무 이력이나 보장된 증거로 사용, 관찰만으로 실행 점유 회수·Done 전이, 사용자 백업 정책 결정.

### 입출력 의미와 운영 제약

입력은 run/단계 상태 전이, 실제 변화 timestamp, 마지막 확인 timestamp, 산출물 참조, 경과시간, 대기 사유, 안전한 runner handle 참조, 저장소별 보존 후보 metadata다.
출력은 최근 관찰 snapshot, 확인 시각과 실제 변화 시각의 분리된 표시, 정제된 진단 이벤트, 참조 검사를 통과한 정리 후보 및 성공/실패 조치 기록이다.
업무 이력 저장 실패는 관련 상태 변경을 rollback하고 성공 응답을 금지한다. 진단 로그 저장 실패는 경고/fallback으로 남기되 이미 커밋한 업무를 재실행하지 않는다.
진행 snapshot은 최근 상태를 갱신하고 매 관찰을 업무 이벤트로 누적하지 않는다. 실제 변화가 없으면 change timestamp를 보존한다. 장기 실행 관찰 주기는 60초 이내다.
진단 공통 의미는 UTC, level, component, event, correlation/request/session, operation, outcome, error, retryable, duration과 안전한 대상 참조다. 인증정보·claim token·환경 전체·payload 본문·전체 경로는 금지한다.
로그 파일의 계획상 보존은 1주일이며 파일별 크기·개수 상한을 적용한다. 종료 일반 진행 이력은 3개월 뒤 참조/복구 여부를 확인한다.
미참조 임시 handoff·테스트 이미지는 1주일 뒤 후보가 된다. 유효/참조 중인 결정·계획·지식·증거와 미확인 실행·미처리 결과는 보존한다.
정리 순서는 참조 확인→후보 기록→삭제→결과 기록이다. 임시 자료가 채택 증거가 되면 정식 리소스로 승격한다. 증거 손상/삭제 시 연결된 검증 재사용을 취소한다.
삭제 직전 참조 상태를 다시 원자적으로 확인해 삭제 예약을 기록한다. 예약된 리소스의 신규 참조는 거부/대기시키고 실제 파일 삭제는 DB transaction 밖에서 수행한다. 실패·중단은 journal로 재개한다. 후보 선정 후 새 참조가 생겼으면 삭제하지 않는다.
회전 로그는 시험 증거 저장소가 아니다. 필요한 진단 조각은 manifest 참조가 있는 리소스로 보존한다. DB와 파일 정리를 한 원자 동작으로 가정하지 않는다.

### 기술·연관·시험

최근 관찰은 SQLite run 상태와 연결하되 장시간 외부 작업 동안 쓰기 트랜잭션을 열지 않는다. 정리 작업은 idempotent 후보/결과 식별로 재시작해도 참조 파일을 다시 지우지 않게 한다.
정제는 이벤트 생성 경계에서 허용 필드와 값 필터를 적용한다. 예외 문자열·명령 인수에 포함된 민감값도 제거한다. logger 실패 자체를 숨기지 않는다.
선행은 메인의 로그 필드·event 계약, 실행 상태 전이·correlation 연결, 리소스 manifest와 참조 조회 계약이다. Q7의 recovery 진단과 Q9의 세션 재개 관찰을 연결한다.

**P2-OBS-01** 실행 시작·상태 변화·대기·오류·완료가 관찰되고, 대기 이유·다음 행동·사용자 결정 필요성이 판독된다.
**P2-OBS-02** 실제 변화가 없는 60초 관찰도 last_seen을 갱신하지만 last_changed는 이전 timestamp를 유지한다.
**P2-OBS-03** 진단 파일 쓰기 실패는 경고/fallback, 업무 이력 저장 실패는 rollback·실패 응답을 낸다.
**P2-OBS-04** 민감 입력·예외·경로가 정제되며 지시 본문·비밀·환경 전체가 로그에 남지 않는다.
**P2-OBS-05** 보존 기간·회전 상한과 참조 증거 예외, 미처리 실행 보존을 시험한다.
**P2-OBS-06** 참조 확인/정리 중 강제 종료 후 재개해도 참조 증거가 삭제되지 않고 고아·실패 후보가 진단된다.
**P2-OBS-07** snapshot 누락·손상은 관찰 실패로 표시하며 마지막 실제 진행을 현재 진행으로 위장하지 않는다.
**P2-OBS-08** 정리 후보 선정과 삭제 사이 신규 참조를 경쟁시켜 참조 자료가 삭제되지 않고 예약/신규 참조가 원자적으로 조정되는지 확인한다.

제안 event는 `run.observed`, `run.progress_changed`, `diagnostic.write_failed`, `retention.candidate_found`, `resource.cleanup.completed`, `resource.cleanup.failed`다. 공통 이벤트 표준은 메인이 확정한다.
추적 필드 의미: event/correlation/run 및 작업 ID, stage/state, last_seen/last_changed, 대기 이유 코드, 결과 참조, 대상 종류·개수, retention 기준 시점, reference check, manifest ID, 오류 등급·retryable, 정리 outcome.
완료 인계에는 관찰 지연과 timestamp 의미 검증, 실패 경로 결과, 실제 보존/정리 검증 근거, 민감정보 스캔 결과의 참조와 미처리 항목을 포함한다.
자율 보고 경계: 비밀 노출 가능성, 참조 인덱스 불일치, 미확인 실행 정리 요청, 보존 정책 변경은 메인에 즉시 보고하고 삭제/정책 확장을 멈춘다. 단순 회전 실패·안전한 임시 후보는 결과와 함께 자율 보고한다.

## Q9 — 전체 통합·제품 패키징·실제 세션 수용

### 목적과 범위

Q9는 Q7/Q8 및 계획·graph·routing·runner·Queue 산출물을 통합하고 2단계 전체 범위가 세 제품에서 실제로 받아들여지는지 판정한다.
추가 범위: 의존성 순서 통합, 제품별 패키지/설치/갱신/제거 검토, 실제 세션 배정→결과 수신→취소/재개 경로 시험, 회귀·manifest·전체 완료표 작성.
수정 범위: 연결부가 공통 서비스를 통해 호출되고 결과·증거가 공통 계약으로 복귀하도록 통합한다. 제품별 연결 실패가 core 동작 성공으로 둔갑하지 않게 상태를 구분한다.
삭제 범위: fixture 결과를 native 통과로 집계하는 방식, 실제 제품 확인 전에 전체 완료를 표시하는 방식, 제품마다 독립 업무 상태 판정을 복제하는 흐름을 금지한다.
Goal: 정의된 전체 요구와 연결부가 구현되고, Codex·Claude Code·OpenCode 각각의 실제 설치/세션/실행 수용 여부 및 미해결 차이를 증거로 판정한다.
Non-goal: 미설치 제품의 성공 추정, 사용자 운영 환경 덮어쓰기, 허용되지 않은 API 호출, 실제 사용자 설정·DB를 시험 root로 재사용, 완료를 위한 범위 축소.

### 입출력 의미·제약·기술

입력은 승인된 공통 계약과 단계별 산출물·시험 정의, 격리된 환경 지문, 제품 연결/버전 식별자, 실제 세션 권한, 검증 재사용 후보다.
출력은 제품별 상태(`passed`, `blocked`, `not_run` 또는 실패), 실제 실행 경로·모델 식별 참조, 단계별 evidence manifest, 통합 결함·영향, 전체 완료 판정과 미해결 목록이다.
제품 수용은 실제 설치·실제 새 세션·실제 권한 경계로 수행한다. fixture/mocked transport 통과, 단위·통합 통과는 native 제품 통과와 별도 계층이다.
미설치·인증·권한·제품 API 접근 부재는 해당 제품을 `blocked`; 아직 실행하지 않은 항목은 `not_run`; 실행해 실패한 것은 실패로 남긴다. 어느 상태도 통과로 변환하지 않는다.
기존 유효 증거는 동일 대상·환경·입력·검증 정의와 commit/dirty 기준이고 후속 무효화가 없을 때만 재사용한다. 제품 버전·세션 경계·권한이 달라지면 해당 native 시험을 다시 한다.
세 제품 모두 실제 호출 경로에서 업무 할당, 실행 식별, 결과 회수 및 상태 연결을 확인한다. 제품 기능 차이·미지원 조합은 사용 가능한 공식 근거 또는 직접 시험으로 기술하고 공통 경로의 성공과 섞지 않는다.
통합은 공통 저장·상태 판정을 재사용한다. 새 dependency·제품별 포장 변경은 공식 근거, 대안, 설치/업데이트·제거 영향과 격리 시험을 함께 제시한다.

### 선행·시험·전체 완료

선행은 Q7 기준 갱신/recovery, Q8 관찰·보존, graph/schema/runner/queue 공통 계약 승인과 독립 검증 근거다. 미확정 공통 인터페이스는 메인이 결정하기 전 소비자 계약으로 고정하지 않는다.
연관은 1단계 기존 검증·설치 규약, 모든 P2 필수 시험, Q7의 P2-GIT/P2-DATA, Q3의 P2-STEP, Q8의 P2-OBS 및 각 제품 실제 인증/권한이다.

**P2-NATIVE-21** Codex의 실제 격리 설치 및 새 세션에서 지원 경로를 할당하고 결과를 회수한다.
**P2-NATIVE-22** Claude Code의 실제 격리 설치 및 새 세션에서 지원 경로를 할당하고 결과를 회수한다.
**P2-NATIVE-23** OpenCode의 실제 격리 설치 및 새 세션에서 지원 경로를 할당하고 결과를 회수한다.
**P2-NATIVE-24** 각 제품의 취소·세션 종료·재개 및 늦은 결과 처리를 실제 경계에서 확인한다. 미지원 시 blocked 사유와 요청된 권한/환경을 기록한다.
**P2-NATIVE-25** fixture, mocked integration, 실제 제품 세션 결과가 서로 다른 증거 계층·상태로 manifest에 남는다.
**P2-NATIVE-26** 제품 설치/업데이트/제거 후 재설치 경로와 제품 호출 뒤 회귀를 격리 환경에서 확인한다.
**P2-DATA-16** 전체 Work/Item/Step 판정과 하위 evidence 적용 여부를 별도로 집계해 부분 통과를 전체 완료로 승격하지 않는다.

전체 scope는 2단계 요구·Item·필수 시험·세 제품 연결 기준 모두에 추적돼야 한다. 예정 시험의 실제 기록, 종료 코드, 환경·입력·commit/dirty 지문, 증거 참조가 있어야 판정한다.
2단계 완료는 정의된 전체 기능·제품 연결의 구현과 시험이 완료되고 실패·blocked·not_run 미해결이 없는 경우다. 일부 prototype, 대체 fixture, 한 제품 성공은 전체 완료가 아니다.
회귀는 영향 받은 계약부터 실행하되 필수 전체 scope 항목 누락 여부를 확인한다. 유효 증거를 재사용하면 manifest와 적용 근거를 남기고 중복 실행을 피한다.
제품별 실측 성공이 아직 없으면 성공으로 쓰지 않는다. 제한된 환경에서는 각 제품을 `blocked` 또는 `not_run`으로 남기고 전체 완료 조건 미충족으로 보고한다.

### 로그·인계·자율보고 경계

제안 event는 `integration.started`, `package.validated`, `native.session.started`, `native.result.received`, `native.cancel.confirmed`, `acceptance.scoped`, `acceptance.completed`다. event name과 공통 schema는 메인이 통합 소유한다.
추적 필드 의미: correlation/request/session/run, 제품/연결 버전 참조, 실제 route/agent/model, 지시·계획 버전, 시험 ID·계층·상태, 입력/환경 fingerprint, 시작/종료 확인, 취소 확인, 증거 manifest, 재사용 사유, 전체 scope 판정.
완료 인계에는 제품별 결과 상태, 실제/fixture 구분, 시험 ID·명령·종료 코드·시간·환경, 증거 참조, 통합 결함·blocked/not_run, 미해결·재현 정보, 실제 변경 영역과 Git 상태를 포함한다. 전체 완료와 사용자 데이터의 PMT 최종 상태 반영은 메인이 맡는다.
작업자는 승인 범위의 통합 충돌과 제품별 안전한 연결 문제를 자율 수정·보고한다. 공통 schema/API 변경, 사용자 권한 확대, 제품 실제 경로를 fixture로 대체할지 여부, 전체 완료 예외는 메인에게 근거와 영향·대안을 보고하고 승인을 기다린다.

## 메인 통합 인계

Q8은 Q1 뒤 로그·관찰 기반을 독립 개발하고 Q7/Q5/Q6과 후속 통합한다. Q9는 모든 의존 기능이 연결된 뒤 수행하며 공유 계약·파일·DB 스키마는 메인 소유로 직렬 확정한다.
각 묶음은 구현과 시험 증거를 구분해 전달한다. 메인은 근거 적용성, 전체 요구 scope, 미해결 차단, 제품별 실제 수용을 확인한 뒤에만 2단계 완료를 기록한다.
