# 2단계 상세계획: 계획·Step·완료 판정

상태: 예정 계획. 구현 여부나 시험 성공을 뜻하지 않는다.
기준: [2단계 범위](../02-model-routing.md), [데이터 계약](../pmt-docs/data-contracts.md), [구조·기술](../pmt-docs/architecture.md), [개발·검증](../pmt-docs/development.md).

## 범위와 경계

이 계획은 PMT 개발 2단계의 planning과 계획 결과를 실행 가능한 관리 단위로 연결하는 기능을 다룬다.
제품 단계 `prototype / 기능 확장 / production`은 각 프로젝트 기능의 적용 범위이며 PMT 개발 1·2·3단계와 별개다.
자연어 요구사항 트리는 사용자 목표·범위·대전제를 기록하고, 구현 트리는 이를 충족할 기술·기능·방법·작업 관계를 기록한다.
두 트리 종료 뒤 프로젝트의 `docs/pmt-docs/` 문서와 UTF-8 JSON graph가 해석 기준이며, PMT에는 ID·버전·참조·hash를 연결한다.
Work는 사용자 결과, Item은 요구·제약, Step은 방법이 정해진 실행 단위다. Item은 재귀 가능하고 run은 Step의 실행 이력이다.
이 계획 묶음은 Q2(두 트리와 조사·선택·명세·graph·프로젝트 문서), Q3(Step 지시·태그·완료 검토·대전제 변경)로 나눈다.
공통 인터페이스의 구체 함수명·공개 타입·스키마·마이그레이션은 메인이 확정한다. 아래는 값의 의미 계약만 정한다.
기능 간 통신은 본체 내부 명시적 호출과 공통 저장 경계를 따른다. 제품 연결부는 형식 변환만 맡는다.

## Q2 — 두 트리와 프로젝트 계획

### 목적·goal

사용자의 원 요구에서 출발해 대전제와 제품 범위를 잃지 않는 자연어 요구 트리를 만든다.
가용 자원 확인과 필요한 조사·실험을 거쳐 요구를 구현 트리, 방법 선택, 기능 명세, Step 후보에 연결한다.
세 종료 조건과 사용자 위임을 명시하고, 종료된 두 트리에서 프로젝트가 유지할 계획 문서와 graph를 만든다.
Goal은 원 요구별 충족 기준, 구현 연결, 미확정 사항, 근거, 종료 이유가 조회 가능하고 Git 원본과 추적이 맞는 상태다.

### 추가·수정·삭제 범위

추가: planning 책임의 요구 수집·분해, 대전제/제품 범위, 조사·실험 결과 반영, 방법 선택, 기능 명세, graph 검증·생성·조회 기능.
추가: 프로젝트 문서 제작 및 초안/확정 상태 구분, 두 트리 노드와 Work/Item/Step 참조를 잇는 관계 관리.
수정: 기존 Project/Work/Item 문맥 조회·생성 경계가 계획 ID·버전·근거 참조를 연결하도록 확장한다.
수정: 검증·리소스 경계가 조사 결과와 재사용 가능한 증거 참조를 계획 노드에 연결한다.
삭제: Git graph/문서의 독립 편집본, 중복 요구 노드, 확인되지 않은 방법을 확정안처럼 노출하는 흐름을 허용하지 않는다.
제외: Queue·runner 구현, 외부 관리툴 동기화, Step 지시 원문 저장/편집 UI, 특정 프로젝트의 실제 요구 내용.

### 입력·출력 의미와 제약

입력 `request_context`: 사용자 원문 참조, 목표, 완료 기준, 제약, 우선순위의 의미를 가진다. 비밀·전체 대화 복제는 금한다.
입력 `project_context`: 기존 문서·구조·결정·기준 commit의 참조다. 관찰 사실·확정 결정·제안은 구별한다.
입력 `capability_context`: 연결된 모델·에이전트·도구·권한의 실제 사용 가능 능력이다. 확인되지 않은 가격·지원은 값으로 추정하지 않는다.
입력 `evidence_ref`: 공식 문서, 원본 코드, 재현 시험으로 뒷받침되는 근거의 식별자·출처·범위다. 시장 평가 의견만 비공식 정보원 예외다.
입력 `decision`: 사용자가 확정하거나 위임한 범위와 결정 근거다. 위임은 목표·대전제 변경 권한을 뜻하지 않는다.
출력 `requirement_node`: 고정 ID, 요약(한 줄 50자 이내), 부모, 원문·근거 참조, 대전제, 제품 단계, 충족 기준을 뜻한다.
출력 `implementation_node`: 고정 ID, 해결 요구 참조, 방법·선행 관계·결과 기준·제품 단계를 뜻한다. 요구와 구현은 다대다 연결 가능하다.
출력 `choice_set`: 실현 가능한 방법 후보 각각의 짧은 설명(30자 이내)과 근거·영향이다. 후보는 최소 3개이고 각 설명은 30자 이내다. 가용 대안이 부족하면 부족 사유를 알리고 허수 후보를 채우지 않는다.
출력 `choice`: 사용자의 직접 작성/선택 또는 허용 범위 내 AI 자율 선택의 출처·범위·이유다. 위임된 선택은 재질문하지 않는다.
출력 `spec`: 기능별 입력·출력의 의미, 제약, 불변식, 오류 조건, 관찰 가능한 확인 방법이다. 운영 실값은 계획 예시에 넣지 않는다.
출력 `graph_ref`: 프로젝트 Git 문서의 경로 범위, graph/schema 버전, 문서 기준 참조, hash 및 노드 식별자다. graph 안에 최종 commit을 순환 기록하지 않는다.
출력 `plan_status`: 초안/확정/폐기 등 계획 해석 상태와 버전을 구분한다. 초안은 실행 승인으로 간주하지 않는다.

### 방법·의존·판정

기술: 상위 메인/역할 스킬이 자연어 해석·분해·방법 판단을 수행하고 Python은 구조 검증·버전·저장·문서/graph 생성을 처리한다. UTF-8 JSON으로 graph를 표현하며 별도 graph DB를 두지 않는다. 필요한 조사는 Q4/Q5/Q6의 실행 계약으로 보내고 결과를 메인에 반환한다.
이유: 기존 런타임 의존성을 유지하면서 Git diff, 백업, 리뷰와 재생성을 가능하게 한다.
Git 문서는 사람이 읽는 결정·대전제의 원본이고 graph는 조회·추적 구조다. SQLite는 실행 상태와 적용 기준 참조만 가진다.
validator는 고정 ID 중복, 누락 참조, 부모·분해·실행 의존 순환, 종료 정보 누락, 버전 불일치를 거부한다.
모든 관계를 무차별 비순환으로 제한하지 않는다. 추적·근거 관계는 허용하고 분해·실행 의존만 순환 검사한다.
선행: 메인의 graph 의미·공개 버전·ID 생명주기·저장/원자 게시 계약 승인, 현재 프로젝트 문서 기준 확보.
관련 계약: data-contracts의 두 트리/graph/Git 원본, architecture의 planning·resources 책임, development의 입력·출력·증거 원칙.
Test P2-TREE-01: 요구 분해가 부모 대전제 참조와 50자 요약 제한을 지키고 원문을 참조한다.
Test P2-TREE-02: prototype·확장·production 각각의 범위/기준과 적용 안 함 사유가 구별된다.
Test P2-TREE-03: 종료 이유, 자율 범위, 미확정 사항이 각 종료 노드에서 보존된다.
Test P2-TREE-04: 구현 노드 다대다 요구 연결과 Work/Item/Step 참조가 조회·왕복된다.
Test P2-TREE-05: 후보 3개 이상·각 30자 이하, 직접 작성 선택과 AI 자율 선택이 구별되며 부족한 후보를 조작하지 않는다.
Test P2-TREE-06: graph의 중복 ID·누락 참조·분해/실행 순환·필수 필드 누락을 거부하고 유효 graph를 재조회한다.
Test P2-TREE-07: Git 문서가 기준이며 DB나 관리툴에 별도 graph 본문 사본을 만들지 않는다.
Test P2-TREE-09: 실제 역할 스킬로 요구 수집→보완/선택→조사 결과 반영→두 트리 종료→프로젝트 문서/graph 게시를 연결하고 구조 누락·의미 충돌은 재검토한다. 단순 정해진 JSON 입력 왕복과 구별한다.
Test P2-TREE-08: 초안은 확정 계획으로 실행되지 않고 조사 결과·공식 출처·검증 상태가 추적된다.
로깅: 요구 수집/분해 경계 `planning.requirement_recorded`, 대전제 경계 `planning.premise_recorded`.
로깅: 조사·선택 경계 `planning.research_attached`, `planning.method_selected`, 명세 확정 `planning.specified`.
로깅: graph 게시/검증 경계 `planning.graph_validated`, `planning.project_docs_published`.
추적 필드: event/request ID, project ID, graph/plan version, node ID, actor/decision source, 기준 commit, evidence ID, 결과·오류 분류.
기록은 업무 이력과 진단 로그를 구별한다. 원문·전체 대화·비밀은 기록하지 않고 로그 실패를 삼키지 않는다.
완료: 승인된 계약, graph validator, 세 종료 조건, 문서/graph 조회, 근거 연결이 시험 증거로 확인되고 메인이 범위 적합성을 판정한다.
인계: 구현 전 공개 타입·저장 의미·오류와 이관안을 메인에 제안하고 확정된 시험 ID·로그 필드를 함께 전달한다.
자율 선택: 확정 목표와 위임 범위 안의 구현 방법·표현·증거 기반 후보 순위는 메인/AI가 선택한다.
메인 요청 경계: 목표·제품 범위·대전제 변경, 공식 근거 상충, 프로젝트 간 공유 계약, schema 호환성·기준 문서 변경은 근거·영향·대안을 메인에게 올린다.

## Q3 — Step 지시, 계층 태그, 검토, 대전제 변경

### 목적·goal

구현 Step은 확정 구현 계획에서 만들고 실행 직전에 지시 버전을 고정한다. 조사·실험 Step은 두 트리 확정 전에도 탐색 범위·판정 기준·권한을 승인한 지시로 배정할 수 있다.
Work/Item/Step의 종류 태그와 분류를 구분해 탐색성을 제공하고 상태·owner·우선순위와 혼용하지 않는다.
Step 증거, Item 요구 충족, Work 통합 결과를 각기 검토하며 오래된 계획 결과로 완료시키지 않는다.
대전제 변경은 영향 범위를 추적해 관련 실행을 멈추고 재계획하되 무관한 근거와 위임된 선택을 보존한다.
Goal은 지시·계획 버전이 일치하고 각 완료 경계에 근거가 연결되며 변경 영향과 후속 조치가 회수 가능한 상태다.

### 추가·수정·삭제 범위

추가: 실행 전 Step 지시 작성·버전 고정·내부 리소스 참조, 계층별 분류 태그 정의·검색 기능.
추가: Step 결과 검토, Item 충족 판정, Work 통합 완료 판정, 대전제 변경 영향 분석·중지·재계획 기능.
수정: lifecycle/verification 경계가 Step 실행 시도와 업무 계층의 revision·계획 버전을 분리해 판정한다.
수정: execution·reconciliation이 오래된 지시 거부, 영향 Step 중지, 미확인 Git commit 반영과 검토 기준 갱신을 사용한다.
삭제: Step 지시 원문을 SQLite, 관리툴, 외부 동기화 본문에 복제하는 경로와 태그만으로 상태/완료를 바꾸는 경로.
제외: 하위 실행 경로 자체, 외부 제품별 UI, Git 원본 문서/Step 지시 원문을 관리툴에서 편집하는 기능.

### 입력·출력 의미와 제약

입력 `approved_plan_ref`: 확정 계획/graph 노드와 기준 commit·버전·hash 참조다. 구현 착수에는 초안, 폐기, 불일치 버전을 거부한다. 조사·실험은 승인된 탐색 지시와 초안 기준을 참조하되 구현 승인으로 승격하지 않는다.
입력 `step_scope`: 목표·포함/제외 범위·공유 변경 경계·선행 의존성·자율 한도다. 실제 파일 위치를 미리 강제하지 않는다.
입력 `instruction_context`: 목적, goal/non-goal, 입력·출력 의미와 제약, 방법·이유, 선행 계약, 시험·로그, 완료·인계 기준이다.
입력 `classification`: Work/Item/Step별 종류 태그와 프로젝트 분류 참조다. 상태·우선순위·담당·모델·의존성은 별도 의미다.
입력 `result_package`: Step/attempt ID, 지시 버전, 실제 실행 식별, 산출물·시험 결과·증거·commit/dirty 상태·미해결 사항이다.
입력 `premise_change`: 바뀐 기준·출처·확정 주체·시점과 영향 후보 노드/문서다. 미확정 제안은 확정 변경으로 처리하지 않는다.
출력 `instruction_ref`: Step ID, 버전, hash, 내부 리소스 위치의 참조와 실행 필요 범위다. 지시 원문은 관리 조회/외부 관리툴에서 제외하며 허용된 runner에는 필요한 범위만 전달한다.
출력 `tag_assignment`: 단계별 종류 태그, 분류 ID와 적용 범위다. 태그는 검색 메타데이터이며 업무 상태를 대체하지 않는다.
출력 `review_decision`: 기준별 pass/fail/blocked/not_run, 검토자, 증거 참조, 현재 적용성이다. 모델의 자기 성공 주장은 증거가 아니다.
출력 `completion_state`: Step 실행 검토, Item 요구 충족, Work 통합 판정을 독립적으로 나타낸다. 하위 완료를 상위 완료로 자동 승격하지 않는다.
출력 `impact_set`: 영향 노드·Step·문서·검증과 영향 이유·판정 버전이다. 무관 가지는 포함하지 않는다.
출력 `replan_action`: 영향 배정 중지/진행 중 실행 중단 요청/확인, 구 결과 보존, 재계획 및 증거 재사용 무효화 범위다.

### 방법·의존·판정

기술: Step 지시는 버전별 내부 리소스로 원자 게시하고 DB에는 참조·hash·상태만 기록한다. 프로젝트 문서는 Git으로 관리한다.
이유: 실행자가 필요한 원문은 안전하게 읽되 관리툴·외부 연동에 원문이 누출되거나 독립 사본이 생기지 않는다.
계층 태그는 Work 목표 종류, Item 요구 종류, Step 실행 종류를 구분한다. 분류 기준은 프로젝트별로 선택하고 고정 ID로 이름 변경을 견딘다.
완료 판정은 요구 기준과 현재 지시/계획 버전, 증거 지문을 비교한다. 상태·claim 변화만으로 검증을 무효화하지 않는다.
대전제 변경 적용 시 점유·실행 계약을 따른다. 실행 중 Step은 중단 요청 후 확인하며 시간 초과만으로 해제/완료하지 않는다.
Git 반영은 lock 후 미확인 commit 분석, 관련 문서·graph·Step·증거 영향 반영, 검토 기준 저장 순이다. dirty 변경은 보존한다.
선행: Q2 확정 graph/계획, 메인의 Step·상태·점유·리소스·이력·검증 공통 계약 및 schema 이관 승인.
관련 계약: execution-contracts의 runner/Queue/lock, data-contracts의 Git·버전·원문 원본, development의 Step 인계·시험 증거 계약.
Test P2-STEP-01: 구현은 확정 계획, 조사는 승인 탐색 지시에서만 Step을 만들고 내부 원문 참조·버전·hash를 고정한다.
Test P2-STEP-02: 외부 관리 응답/동기화에 지시 원문이 없고 Step ID·상태·참조·결과만 존재한다.
Test P2-STEP-03: Work/Item/Step 태그·분류 검색이 상태·우선순위·owner와 분리되고 이름 변경에도 ID 관계가 유지된다.
Test P2-STEP-04: 지시 버전이 오래되었거나 graph 기준이 바뀐 결과를 보존하되 현재 계획 완료에는 적용하지 않는다.

인계: 메인에게 계약 변경안·호환성·관련 시험·로그 필드를 제안하고, 작업자는 실제 범위·증거·dirty 상태·잔여 쟁점을 반환한다.
자율 선택: 지시 표현·태그 사전의 프로젝트별 확장·영향 후보 계산은 확정 계약 안에서 메인이 정한다. 명확한 승인 범위 오류는 작업자가 고친다.
메인 요청 경계: 대전제/사용자 목표 변경, 영향 판정 논쟁, 완료 기준 변경, 공통 schema·상태·lock·로그 계약 변경은 즉시 근거·영향·대안과 함께 보고한다.

## 구조·요구 변화와 긴급 복구

모듈 경계·공통 통신/데이터 계약·핵심 기술·운영 보존 정책이 바뀌면 해당 구현을 확정하지 말고 메인에게 근거, 영향, 대안을 올린다.
사용자 목표나 대전제 확정은 사용자 결정이 필요하다. 이미 위임된 목표 내부의 방법 선택은 자율 처리하고 사용자에게 재질문하지 않는다.
일반 계획의 두 종료 경계는 자연어 트리에서 다음 분해가 구현 방법 선택일 때, 구현 트리에서 다음 분해가 직접 파일 수정 지시일 때다.
어느 트리든 사용자가 이후 결정을 위임한 노드는 자율 범위와 종료 이유를 남기고 분해를 마친다.
긴급 복구는 문서 부족이나 계획 완성을 기다리지 않는다. 관찰된 사실·확정 결정·제안, 대상·권한·복구 기준을 구분해 최소 복구를 수행한다.
복구 중 공유 계약·대전제·사용자 데이터 의미를 바꿔야 하면 메인에게 즉시 알리고 안전한 범위의 복구를 이어간다.
긴급 변경의 실제 증거·시험·commit/dirty 상태를 남기고, 복구 뒤 영향받은 계획·graph·문서·검증을 정리해 후속 Step으로 인계한다.
