# F11 Host boundary audit

Read-only design note based on `docs/phase3/spec-host-integration.md`, `docs/phase3/plan-host-integration.md`, and the current source. It records code facts separately from proposed Host behavior. No credential values, settings, or external service data were read.

## Confirmed in current code

- `LocalStore` in `src/pmt/store.py` is an operation-level adapter: `execute(request)`, `get_request_result(request_id, actor, session_id)`, and `check_compatibility()`. `src/pmt/service.py` normalizes protocol-v1 and dispatches through the full Phase 2 and Phase 3 operation registries. `Database.run_request` fingerprints the normalized request and commits both the business result and complete response JSON in `requests`; replay is restricted to the stored actor/session and a matching request fingerprint.
- `lifecycle.claim_task` in `src/pmt/lifecycle.py` generates a raw `claim_token`, stores only its SHA-256 in `claims.token_hash`, then returns the raw token. `release_claim`, `finish_task`, and `recover_claim` rely on that value. Since `run_request` persists the complete handler response, the local request replay row also contains the raw claim token. Thus “hash-only claim storage” is not true for the complete persisted request path today.
- `execution.service` has useful state transitions: `_prepare` checks run revision/dependencies, acquires scope locks, and transitions the run; `_attach` records an owner-bound handle; `_observe` records telemetry without changing authoritative state; `_submit_result` checks pinned directive version, actual route, every criterion, and ready evidence refs; `_cancel` requests cancellation without claiming a process has stopped.
- Runtime effects are local. `runners.service` dispatch writes private spool/config files and may start the selected CLI; poll reads the local spool/receipt and publishes result resources; cancel writes the local control file and waits for stop evidence. `LocalExecutionRuntime` calls that service with `local_store.db`; its process observation is explicitly separate from run-state mutation.
- `Phase3Storage` persists scoped, owner-bound objects, journals, and outbox entries, but it accepts a `Database` and current F3–F7 services directly use SQLite and/or workspace paths. `LocalStore` cannot currently be replaced by `HttpStore` for every registered operation without separating these state and local-effect paths.

## Proposed split and allowlist

Keep a small `StorePort` with the current `execute`, `get_request_result`, and `check_compatibility` meanings. `LocalStore` remains its current implementation; a standard-library `HttpStore` sends versioned JSON to a Host `/api/v1` adapter and maps HTTP outcomes back to the same protocol envelope/exit semantics. The server derives actor, device, session, and namespace from verified authentication, overwrites or rejects body identity claims, and derives `environment_id` only as a separately registered profile. The HTTP request body cannot select an internal callback or supply a trusted capability.

The Host exposes an explicit registry of DB-backed state operations only: lifecycle record/event/claim transitions; queue/run state transitions and reads; verification and scoped resource-reference operations; owner-scoped request-result lookup; compatibility; and narrowly scoped F5/F6/F7 reference operations once their current-source authorization callbacks use the state port. Each operation gets its own field, size, scope, and current-revision checks. Do not expose a generic all-operations Phase 2/3 dispatcher, arbitrary SQL, filesystem publication, Git operations, setup paths, or `dispatch_execution`/`poll_execution`/`cancel_runner` on the Host. F3/F4 source inspection and document preparation/publication remain client-local; the server may store verified canonical resource refs, manifests, and derived indexes after client-provided source fingerprints are checked.

Add a separate client `LocalRuntime` plus `LocalWorkspaceResolver`. Host `prepare_execution` remains the authority for current run revision, owner, dependencies, canonical logical scopes, and claim. It returns a versioned, immutable, path-free `RuntimeContext` binding run/source/directive/context/evidence refs. A private runtime-context read is limited to that active owner and pinned versions; it is not a general `read_step_directive` endpoint. After an authorization callback confirms the current run/claim/source, the resolver maps repository and canonical relative resource keys to the environment's local checkout and rechecks containment, Git/SourcePin, dirty state, and path locks before any file access. Absolute paths, argv, environment, PID, and process controls never come from or go to Host.

The sequence is: Host `prepare` returns a current run/runtime ref; client reads only the authorized private runtime context; the local resolver maps canonical scopes and the local runner executes; client `attach` submits an opaque handle ref; observation combines a server state read with a separate local process snapshot; after an observed terminal receipt, client hashes/publishes allowed evidence and submits the result for server validation; Host `read` returns current state; cancel first marks a Host cancel request, then the local runner acts and observes termination, and only confirmed stop/reconciliation can release locks. The Host never infers process state from a client assertion or performs the process action itself.

## Claim replay proposal and assessment

The proposed internal-only token factory is viable with two constraints. Bind the HMAC derivation to a versioned server key plus claim request ID/nonce, body fingerprint, canonical record/scope, authenticated actor/device/session, and claim generation. Keep the key outside the DB/config/logs and store only `token_hash` plus non-secret lease metadata (`claim_ref`, nonce, key ID, owner/device/session, record/scope, state). Retain old key versions while active leases need replay, or reject restore/rotation with active claims. F13 quiescence already requires no active claims, so Host key material need not migrate.

The server must construct the token factory in trusted Python service code; never accept it as an HTTP/request field. For claim creation, an HTTP-specific `run_request` handler calls the existing lifecycle transition with that factory, removes `claim_token` before constructing its cached response, and returns only `claim_ref` plus ordinary state/revision. For release/finish, the handler resolves the ref against the authenticated principal and current active claim, verifies the stored hash, derives the token, and injects it into a short-lived internal request copy only after `run_request` has fingerprinted the sanitized outer request. Cached response, request body, event, outbox, and diagnostics therefore contain no raw token. Post-commit redaction is too late because `run_request` has already stored the response.

`claim_ref` is a locator, never a bearer credential: every use still requires authenticated actor/device/session, current record/scope ownership, active claim, revision CAS, and matching run. Preserve local caller semantics through `HttpStore`: represent the returned remote ref as an opaque adapter claim handle in the protocol-shaped result and translate that handle back to `claim_ref` on later release/finish calls. Keep the existing local token path unchanged. Do not return the derived raw token to clients. A stable HMAC allows same-request recovery after a lost response without persisting a decryptable token; include a key ID and keep the key version until leases expire/release.

## Required tests and failure meaning

- `P3-F11-01`: compare LocalStore and HttpStore envelopes, revisions, result meanings, compatibility, unsupported fields/operations, and local-only runner/filesystem rejection.
- `P3-F11-02`: two independent clients race for one logical scope; replay one request ID with the same body; reuse it with a changed body; lose a response and recover through owner-scoped request lookup; test stale owner/revision, claim recovery, key-version replay, and assert raw claim token appears only in transient local memory (never Host request cache, journal, outbox, diagnostics, or logs).
- `P3-F11-03`: actual isolated HTTP/HTTPS auth and scope separation, resource hash/size/read ACLs, device revocation, secret-free logs, and file/DB interrupted-publish recovery.
- Runtime boundary: validate two clients with different local absolute paths mapped to the same canonical repository/resource refs; reject stale SourcePin, path escape, changed claim, and disconnected new work before file I/O. On disconnect, keep already-produced results pending locally; do not mint shared claims. On reconnect, replay the same request ID and recheck current owner/revision/source; preserve conflicts as pending.
- Cancellation boundary: a remote cancel request leaves process action local and locks held; only a verified local terminal receipt plus server reconciliation establishes stopped state.

## Scope limits

This is a source-based design proposal, not an implementation or security test. The agreed acceptance target remains isolated local HTTP/HTTPS with two clients. It does not establish Linux, remote deployment, or production authentication support.
