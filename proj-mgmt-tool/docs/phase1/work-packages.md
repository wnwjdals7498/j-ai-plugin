# 작업 묶음과 지시 계약

각 묶음은 기능 책임과 관찰 가능한 입출력으로 배정한다. 코드 파일 배치는 소유자가 제안하고 메인이 충돌 여부를 확인한다. 공통 계약·시험·로그의 원본은 이 문서에 복제하지 않고 참조한다.

## P0. 공통 계약과 수용 기준 확정 — 메인

- **목적·이유:** 작업자들이 다른 ID·상태·완료 의미를 구현하지 않도록 동일한 판단 기준을 만든다.
- **입력:** 사용자 합의, 기존 단계 계획, 제품·Python·SQLite 공식 근거, 3개 병렬 검토 결과.
- **출력:** 승인된 계약 버전, 상태/오류/로그 목록, 작업 의존성, 시험 ID, 지원 대상·미확인 목록. 구현 착수의 기준점이다.
- **기술·관계:** [공통 계약](contracts.md), [검증](verification.md), [로깅](logging.md), [제품 규약](adapters-packaging.md). 모든 묶음이 소비한다.
- **검증·증거:** 계약 필드·상태·종료 코드·시험 기대값 간 모순 확인. 불명확한 제품 필드는 fixture 조사 항목으로 남긴다. 문서 검토 결과와 공식 출처·확인 시각을 기록한다.
- **완료:** G0. 공유 변경 책임과 소비자의 입력/출력이 명확하다. 스키마·물리 구현은 P1의 산출물이며 임의 선행 작성하지 않는다.

## P1. 저장 기반·식별·스키마·공통 진단

- **목적·이유:** 안정 ID·관계·revision·저장 제약을 제공해 뒤 작업의 중복 방지와 동시성 계약을 지탱한다. 진단 로그도 각 구현이 같은 형식으로 호출하게 한다.
- **입력:** P0의 논리 데이터·ID·스키마 버전·데이터 경로·maintenance·로그 계약.
- **출력:** 신규 초기화와 버전형 이관, DB 연결/트랜잭션 경계, 필요한 관계·고유 제약, 환경/저장소 등록, 공통 로그 수신 인터페이스. 재실행 후 같은 DB·환경 ID를 반환한다.
- **기술:** Python `sqlite3`, UUID, JSON, pathlib, logging. foreign key·transaction·busy 정책을 명시하고 startup에서 실제 runtime을 확인한다.
- **관계·제외:** 선행 P0. P2·P3·P4·P5가 소비한다. 사용자 대화 판정·제품 이벤트 매핑·모델 분배를 하지 않는다. 공유 스키마·기반 코드는 이 소유자가 담당한다.
- **시험·로그:** DATA-01~03, LOG-01~02. init/migration/schema version, 데이터 root 별칭, 결과·오류 단계·correlation ID를 기록한다.
- **완료:** 신규/재초기화/구버전·지원 밖 버전 처리가 재현되고, 제약 오류·이관 실패에 기존 데이터가 보존된다. 후속 소비자에게 승인된 호출 계약을 전달한다.

## P2. 상태 변경·멱등성·점유·완료

- **목적·이유:** 여러 세션의 중복 요청·동시 변경·오래된 소유자 때문에 상태와 이력이 갈라지는 것을 막는다.
- **입력:** P1 저장 기반, expected_revision, request/event ID, 명시적인 변경·점유·해제·완료 요청, 리소스·검증 조회 계약.
- **출력:** 상태와 event·request 결과의 원자적 반영, 현재 claim token, 충돌/오류, 재시도 가능한 원결과, pause/blocked의 다음 조치.
- **기술:** 짧은 SQLite 트랜잭션, 고유 키, 조건부 revision 갱신, token 비교. 모델 호출·파일 복사 동안 DB 트랜잭션을 유지하지 않는다.
- **관계·제외:** 선행 P1. P3의 유효 검증 조회와 P4의 ready 리소스 참조를 계약으로 소비한다. P3·P4와 병렬 가능하나 통합 성공은 실제 의존 기능으로 확인한다. 훅 종료·시간 경과로 완료/자동 회수하지 않는다.
- **시험·로그:** TX-01, IDEM-01~02, EVENT-01~02, REV-01, CLAIM-01~03, DONE-01~02, DECISION-01, LOG-03. 대상·이전/이후 revision·actor·request/event ID·commit/rollback/conflict·token 원문 없는 소유권 결과를 기록한다.
- **완료:** 경쟁 점유의 성공자는 정확히 하나, 성공 요청 재전송은 한 번 반영, stale 입력·token은 불변 상태로 거부, 실패 주입 시 부분 반영 없음. 실제 검증·리소스 계약을 연결한 완료 시험을 통과한다.

## P3. 조회·재개 문맥·문서·검증 후보

- **목적·이유:** 다음 세션이 필요한 근거만 읽고, 같은 조건의 검증을 다시 수행하지 않도록 조회한다.
- **입력:** P1 기록·관계, 선택 범위/Item, query·예산·cursor, 검증 정의와 대상·환경·입력 지문. P2의 실패·철회 이벤트, P4의 리소스 상태.
- **출력:** 현재 상태·결정·다음 작업·주의·근거 ID, 결정/파기/원리/테스트/README/Item 문서 조회, 일치하는 검증 후보와 재사용 가능/불가 이유.
- **기술:** SQLite 조회·안정 순서·pagination, JSON/Markdown 출력, SHA-256 기반 canonical 지문. 실제 dirty 파일 상태·명령·의존성·환경·입력·정의 버전을 비교한다.
- **관계·제외:** 선행 P1, P2·P4와 병렬. 공유 스키마를 직접 바꾸지 않는다. 링크는 고정 ID를 사용한다. LLM의 영향관계 추론·원격 동기화를 만들지 않는다.
- **시험·로그:** READ-01~02, VERIFY-01~03. query 범위·반환 수·예산 축소·조회 revision, 검증 ID·match/mismatch/stale 이유를 기록한다.
- **완료:** 범위 밖 자료를 섞지 않고 핵심 경고·기준을 보존한 요약을 반환한다. 동일 조건의 유효 근거만 재사용하고 미확인 조건·이후 실패·증거 소실은 거부한다.

## P4. 리소스·정리 기반·백업·복원

- **목적·이유:** 이미지·로그·증거를 중복 본문 없이 보관하면서 부분 실패·업데이트에서도 참조와 복구 가능성을 유지한다.
- **입력:** P1 기반, 파일/허용 메타데이터, 범위·hash·보존 분류, 참조 변경, maintenance 운영 계약.
- **출력:** staging/ready artifact ID, hash·크기·참조, 고아/누락/손상 진단, 정식 근거 승격, 일관된 백업 manifest와 격리 복원 결과.
- **기술:** pathlib·hashlib·제한된 파일 I/O, SQLite backup API, manifest 검증. DB와 파일을 하나의 트랜잭션으로 간주하지 않는다.
- **관계·제외:** 선행 P1, P2·P3와 병렬. P2가 제공한 원자적 참조 변경 규약을 소비한다. 초기 자동 GC는 지연하고 먼저 diagnose/정리 대상 제안을 만든다. 사용자 데이터의 실제 파기는 이 작업의 기본 실행이 아니다.
- **시험·로그:** RESOURCE-01~03, BACKUP-01~02. artifact ID·hash·크기·단계·참조 수·백업 ID·schema·검사 결과를 기록한다.
- **완료:** 파일 성공/DB 실패·프로세스 종료 지점에서 고아를 찾을 수 있고, ready DB 참조에 누락 파일을 숨기지 않는다. DB+리소스 roundtrip에서 ID·관계·hash가 일치한다.

## P5. 로컬 CLI·JSON 계약 통합

- **목적·이유:** 제품·스킬·미래 HttpStore가 같은 의미로 본체를 사용할 수 있게 한다.
- **입력:** P2~P4의 승인된 operation, request/response·오류·종료 코드, 데이터/runtime 설정.
- **출력:** 실제 프로세스로 실행되는 machine CLI, stdout JSON 한 줄, stderr 진단, 정확한 exit code, 원결과 재조회. 다른 cwd·공백 경로에서도 같은 data root를 사용한다.
- **기술:** Python 진입점, argparse 또는 동등한 단순 명령 처리, UTF-8 JSON, subprocess 시험. 사용자 입력을 문자열 shell 명령으로 조립하지 않는다.
- **관계·제외:** 선행 P2·P3·P4. P6·P8의 접점이다. 제품별 native hook JSON과 본체 JSON을 섞지 않는다. MCP·HTTP 서버·모델 호출은 이 단계에 추가하지 않는다.
- **시험·로그:** CLI-01~03, RECOVER-01, LOG-01~03. operation·request ID·경과 시간·exit code·오류 분류를 남긴다. parse 불가이면 request ID가 없음을 명시한다.
- **완료:** 실제 stdin/stdout 왕복·잘못된 입력·진단 실패·프로세스 재시작 시험에서 CLI 계약과 DB 결과가 일치한다.

## P6. 제품별 이벤트·훅 연결 — 세 독립 묶음

Codex, Claude Code, OpenCode를 각각 소유자에게 배정한다. 공유하는 의미는 같지만 native 입력·출력·등록 방식은 [제품 규약](adapters-packaging.md)을 따른다.

- **목적·이유:** 사용자 지시·세션·응답 이벤트를 PMT에 연결하되 제품 생명주기와 업무 완료를 혼동하지 않는다.
- **입력:** 제품·버전별 공식 이벤트 fixture, P5 CLI 계약, 연결부 설정·timeout·재전송 정책.
- **출력:** normalized event·안정 식별자·출처·허용 payload, native 반환, 한정된 재전송함, 지원 이벤트 표. 사용자 선택은 명시적 저장 절차로 연결한다.
- **기술:** Codex·Claude의 command hook 연결, OpenCode의 stable JS plugin와 CLI 프로세스 호출. 실제 제품이 제공하는 runtime을 사용한다.
- **관계·제외:** fixture·공식 지원 조사만 P0과 병렬 준비 가능. 실행 연결은 P5 후. DB 직접 접근, Stop/idle 자동 Done, 전체 transcript 수집, 모델 분배는 하지 않는다.
- **시험·로그:** EVENT-01~02, STOP-01, HOOK-01~03. 제품·연결부 버전·원 이벤트 식별·정규화 종류·경과·저장/대기/유실 상태를 기록한다.
- **완료:** 정상/중복/역순/미지원/DB 실패 fixture에서 정의된 결과를 반환하고 업무 완료를 만들지 않는다. 제품의 실제 활성화는 P9에서 따로 검증한다.

## P7. 본체·연결부 통합 검증 — 메인 책임

- **목적·이유:** 개별 작업의 성공을 실제 전체 동작으로 연결하고, 모의 의존 기능 때문에 숨겨진 실패를 찾는다.
- **입력:** P1~P6 산출물·계약 버전·개별 시험 증거, 깨끗한 격리 데이터와 fixture.
- **출력:** G1 시험 결과 묶음, 실패/blocked 목록, 대상 commit·dirty 지문·runtime·명령·증거 manifest. 스키마·CLI·정규화 결과가 하나의 계약으로 동작함을 입증한다.
- **기술:** pytest, 실제 SQLite·독립 subprocess, 재현 가능한 실패 주입, 표준 로그·증거 수집.
- **관계·제외:** 준비 데이터는 P0 후 병렬 작성 가능. 성공 판정은 P1~P6 통합 후. 실제 제품 설치 검증은 G3이며 fixture로 대체하지 않는다.
- **시험·로그:** [G1 필수 시험](verification.md#검증-단계). 개별 실패와 해당 계약·상관 ID·진단 로그·DB 검사 결과를 연결한다.
- **완료:** G1 필수 시험 통과, 실패의 원인과 변경·재시험이 증거로 설명됨. 관련하지 않은 전체 시험을 근거 없이 반복하지 않는다.

## P8. 작업 스킬·패키징·로컬 setup

- **목적·이유:** 검증된 본체를 여러 에이전트·설치 위치에서 재사용하고 업데이트 시 사용자 데이터를 보존한다.
- **입력:** G1 통과 본체·CLI·연결부, 제품·버전·프로필 scope별 공식 설치/update/remove 경로, 공통 버전·데이터 경로·setup 계약.
- **출력:** 제품별 설치 패키지, 문맥 조회/점유/결정/완료 스킬, runtime·저장·연결 점검 결과, manifest/버전/의존성 검증 증거. 코드와 DB 경로를 분리하고 package 교체·DB 이관·cache/등록 제거의 제어 범위를 구분한다.
- **기술:** 단일 Python 본체, 제품별 manifest·skills·hook 설정, 필요한 OpenCode JS package. build 도구·의존 버전은 검증한 값으로 고정한다.
- **관계·제외:** 선행 G1. 공통 버전·데이터 계약은 단일 소유, 제품별 패키지는 병렬 가능. native 훅의 신뢰·활성화를 자동 승인한 것으로 가정하지 않는다. 실제 설치는 승인된 격리 테스트 범위에서 P9가 확인한다.
- **시험·로그:** PKG-01, CLI-03, INSTALL-01 준비. artifact ID·package hash·제품/연결부/core/schema 버전·경로 점검·기능별 ready/blocked 상태를 기록한다.
- **완료:** 개발 checkout에 의존하지 않는 배포물로 검증 가능하고, 패키지 밖 DB·resources를 일관되게 찾는다. 스킬 문구만으로 실행 도구 등록을 완료했다고 하지 않는다.

## P9. 실제 설치·사용·업데이트 검증

- **목적·이유:** 플러그인 설치·권한·훅·새 세션·업데이트까지 작동하는 것을 1단계 완료 증거로 삼는다.
- **입력:** G2 패키지, 제품별 고정 버전·runtime·격리 프로필/데이터, 실제 사용 시나리오.
- **출력:** 제품별 설치→활성화→기록→새 세션 재개→업데이트→제거 후 재설치 결과, 데이터 유지 검사, 지원 표와 미완료 목록. 설치·실사용 로그/화면/CLI 결과를 보존한다.
- **기술:** 제품의 공식 설치·검증·제거 경로, 실제 native 이벤트, 본체 읽기·증거 hash 확인.
- **관계·제외:** 선행 G2. 서로 다른 제품의 프로필·DB·작업 공간이 독립이면 병렬 가능. 실제 사용자 설정·동일 DB를 여러 설치 시험에서 공유하지 않는다.
