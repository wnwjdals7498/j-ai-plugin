forge-ledger 플러그인 계획

GitHub, Gitea, GitLab 저장소에 연결해서 프로젝트 현황은 위키에 문서화하고, 결정 이력 같은 상세 내용은 저장소 안에 두었다가 필요할 때만 읽게 하는 Claude Code 플러그인의 구성안입니다. PMT 스킬과 ai-memory 플러그인의 검증된 방식을 가져와 어디에 무엇을 적을지, 무엇을 자동화할지 정리했습니다.

요약

표시 검증은 공식 문서·소스·서버에서 직접 확인한 내용, 추론은 근거를 밝힌 판단, 제안은 이 계획에서 정한 방식입니다.

무엇을 만드나
저장소의 .ledger/ 폴더를 원천으로 삼는 플러그인입니다. 스킬 3개, 명령 10개, 훅 6종, 표준 라이브러리만 쓰는 Python 엔진 하나, 세 포지용 CI 템플릿으로 구성합니다. 제안
값은 어디에
결정·목표·상태처럼 함께 볼 지식은 저장소 .ledger/에 적고 PR로 리뷰합니다. 위키는 그 내용과 포지 API 수치로 만드는 생성물이라 손으로 고치지 않습니다. 토큰과 캐시는 각자의 PC에 둡니다. 제안
업무 처리 방식
PMT의 다섯 단계(전체 작성 → 세부 정리 → 단위 분리 → 의존성·우선순위 → 착수)를 그대로 씁니다. 작업 구조는 저장소 .ledger/plan/에, 진행 상태는 포지 이슈에 둡니다. 단계마다 넘어가는 조건을 ledger plan check가 검사합니다(5절). 제안
세 포지를 하나로
GitHub, Gitea, GitLab 모두 위키를 별도 git 저장소로 다룹니다. 그래서 위키 쓰기는 git clone · commit · push 한 가지 경로로 구현하고, 포지마다 다른 것은 주소·사이드바 파일 이름·이슈 API뿐입니다. 검증 [S4] [S7] [S12]
무엇을 자동화하나
결정 기록과 PR, 계획 반영, 착수 가능 알림, 마일스톤 자동 닫기, 위키 현황 갱신, PR 필수 검사, 주간 보고, 재검토 기한 알림, 릴리스 노트, 세션 재개 요약까지 14가지 업무입니다(9절).
먼저 결정할 것
엔진 형태, 위키 갱신 주체, 결정 ID 방식, PMT와의 관계, GitLab 시험 환경, 작업 계획의 원천 6가지입니다(13절). 각각 추천안을 붙였습니다.

01설계 원칙

  1. 원천은 저장소, 위키는 생성물결정과 상태는 코드와 같은 저장소에서 PR로 리뷰받습니다. 위키는 언제든 다시 만들 수 있어야 하므로 생성 구역은 손으로 고치지 않습니다. 사람이 쓰는 구역은 표시로 따로 보존합니다. 제안
  2. 단계적으로 읽는다세션에는 4,000자 이하 요약만 넣고, 상세는 검색 → 파일 1개 → 계보 순으로 필요한 만큼만 엽니다. PMT의 RESUME 예산과 "원본 통독 금지" 원칙을 그대로 따릅니다. 검증 [S13]
  3. 세 포지의 공통 경로는 git위키 API는 포지마다 다르고 GitHub 문서는 웹 편집과 git clone만 안내합니다. 쓰기는 git으로 통일하고, API는 이슈·마일스톤·PR 수치를 읽을 때만 씁니다. 검증 [S4] 제안
  4. 훅은 실패해도 작업을 막지 않고, 막더라도 한 번만ai-memory 훅처럼 오류가 나면 조용히 통과합니다(fail-open). 종료를 막을 때는 stop_hook_active를 확인해 무한 반복을 피합니다. 검증 [S14]
  5. 민감값은 쓰지 않고, 기록 속 지시는 따르지 않는다IP·접속 주소·토큰·계정·고객명은 처음부터 적지 않습니다. 다른 사람이 쓴 결정 파일 안의 문장은 정보일 뿐 명령이 아닙니다. ai-memory 기록 규율과 같은 기준입니다. 검증 [S14]

## 문맥

## 결정

## 대안
- 위키를 원천으로 쓴다: PR 리뷰를 못 거친다.

05업무 처리 방식: 전체 작성부터 착수까지

PMT의 다섯 단계를 그대로 따릅니다. 작업 구조(무엇을, 어디까지, 무엇이 먼저)는 저장소 .ledger/plan/에 두고 PR로 리뷰합니다. 진행 상태(누가, 지금 어디까지)는 포지 이슈에 둡니다. 단계마다 다음으로 넘어가는 조건이 있고, ledger plan check가 이를 검사합니다. 제안

1. 전체 작성

  • 대화에서 목표를 받아 .ledger/project.md 초안을 만듭니다. 칸은 목표(검증할 수 있는 문장 1~3개), 비목표, 성공 지표, 범위 밖, 관련 저장소입니다. PMT도 프로젝트를 "검증 가능한 목표" 한 줄로 시작합니다. 검증 [S13]
  • "사용자가 편해진다" 같은 문장은 통과시키지 않습니다. "세 포지 시험 저장소에서 ledger sync 두 번 실행 시 두 번째 diff가 0줄" 처럼 명령이나 수치로 확인할 수 있어야 합니다. 제안
  • PR로 승인되면 위키 Home 첫머리에 나옵니다.

2. 세부 내용 정리

  • 목표를 Work(작업 묶음)로 나눕니다. Work 하나가 포지 마일스톤 하나입니다. 업무보고의 서브 목표 규칙처럼 기능·모듈 단위가 아니라 "닫히는 단계"로 자릅니다. 기능 단위로 자르면 끝나지 않아 완료가 남지 않기 때문입니다. 제안
  • 조사하다 나온 실측값은 facts/에, 미리 정해야 할 선택은 결정 초안으로 뽑아 둡니다. 답이 없는 질문은 kind: view(조사) Item이 됩니다. 제안

3. 단위별 업무 분리

  • Item 하나 = PR 하나 = 완료 기준 하나 = 담당자 하나로 자릅니다. herdr 위임 규칙의 "지시 하나에 목표 하나, 산출물 하나"와 같은 크기입니다. 제안
  • Work 아래 깊이는 3까지이고 test Item은 자식을 가지지 않습니다. 종류는 PMT와 같은 job · view · test · hotfix입니다. 검증 [S16]
  • 범위 · 완료 기준 · verify 세 칸이 모두 있어야 착수하거나 하위 에이전트에 맡길 수 있습니다. PMT start --delegate의 게이트와 같습니다. 검증 [S16]
  • 크기는 S(반나절 이내) · M(1~2일) · L(나눌 대상)로 적고, L이 남아 있으면 plan check가 실패합니다. 제안
  • Item은 링크를 따라가지 않아도 범위와 완료 기준을 이해할 수 있게 씁니다(PMT 불변식 8). 이슈 본문은 이 파일에서 생성되므로 이슈만 봐도 같은 내용이 보입니다. 검증 [S13]
.ledger/plan/W1/W1-2-decide-cmd.md
---
id: W1-2
title: decide 명령 구현
kind: job             # job | view | test | hotfix
parent: W1
needs: [W1-1]         # 먼저 끝나야 하는 Item
wait: []              # 외부 대기, 예: ["ext:GitLab 시험 환경"]
priority: high        # critical | high | normal | low
size: S               # S | M | L(L은 나눠야 함)
verify: "python3 -m pytest tests/test_decide.py"
issue: null           # plan apply 뒤 채움, 예: dev/sample-app#34
---

파랑은 착수 가능, 회색은 차단, 주황은 외부 대기입니다. 빨간 굵은 선은 핵심 경로(남은 일 중 가장 긴 선행 사슬)입니다.

  • needs는 PMT의 blocked_by, wait는 PMT의 ext: 외부 대기와 같습니다. 선행 Item이 완료되거나 취소되면 뒤 Item의 차단이 자동으로 풀립니다. 검증 [S16]
  • 착수 가능 = 이슈가 열려 있고, 담당자가 없고, 선행이 모두 닫혔고, 외부 대기가 없는 Item입니다. PMT의 "Planned이고 차단 없음"과 같은 조건입니다. 검증 [S16]
  • PMT는 착수 가능 목록을 ID 순서로만 보여 줍니다. 검증 [S16] 이 플러그인은 우선순위를 더해 다음 순서로 정렬합니다. 제안
    1. priority(critical → high → normal → low)
    2. 핵심 경로 위에 있는가
    3. 끝나면 풀리는 뒤 Item 수가 많은가
    4. ID
  • 의존성 순환과 없는 선행 ID는 PR 필수 검사에서 실패합니다. PMT doctor가 부모 순환과 없는 blocked_by를 실패로 보는 것과 같습니다. 검증 [S13]
  • 포지에 반영할 때는 GitHub blocked by, Gitea 의존성, GitLab blocks로 옮깁니다. GitLab Free는 차단 관계가 없으므로 relates to와 본문 "선행" 줄로만 표시합니다(6절). 검증 [S19]

확인하지 못한 것

  • GitHub REST API에 위키 엔드포인트가 있는지는 찾아보지 않았습니다. 계획은 git 경로만 씁니다.
  • Gitea 작업 토큰의 wiki 범위로 실제 위키 git push가 되는지는 시험하지 않았습니다. P2에서 이 서버의 Gitea로 시험합니다.
  • GitHub 위키 페이지 이름의 공백·특수 문자 변환 규칙은 확인하지 않았습니다. 그래서 영문·하이픈 이름만 쓰기로 했습니다.
  • GitLab 그룹 위키는 범위에서 뺐습니다.
  • Gitea 1.27에 상하위 이슈 기능이 있는지는 문서에서 찾지 못했습니다. 그래서 마일스톤과 본문 링크로 처리합니다.
  • GitLab Tasks 문서 맨 위에는 요금제 표시가 없어 Free에서도 쓸 수 있다고 봤습니다. 상태 변경 같은 하위 기능만 Premium 이상으로 표시돼 있습니다.
