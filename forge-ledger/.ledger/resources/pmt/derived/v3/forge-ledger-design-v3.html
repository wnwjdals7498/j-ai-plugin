forge-ledger 설계서 v3

Plane(작업·문서), Gitea(코드·실제 문제), Figma(화면)를 잇고, 정보를 모아 한 대시보드로 보여 주는 Claude Code 플러그인의 설계입니다. 앞부분은 제품 요구사항 문서(PRD, Product Requirements Document), 뒷부분은 구현 문서 8종입니다. 구현은 아직 하지 않습니다.

검증 공식 문서·서버에서 직접 확인 추론 근거를 밝힌 판단 제안 이 설계에서 정한 방식(작성자 판단) 결정 사용자가 정한 것(PMT 결정 번호)

하지 않을 것(비목표)

  • Plane이 이미 하는 작업 관리 기능을 다시 만들지 않습니다. 허브는 모으고 연결해서 보여 주기만 합니다.
  • 코드 리뷰 도구나 화면 설계 도구를 만들지 않습니다.

실패로 보는 경우(반목표)

  • 대시보드가 원천이 되는 경우. 상태를 바꾸는 일은 각 도구에서 하고, 허브는 읽기 전용입니다.
  • 같은 내용을 사람이 두 도구에 두 번 입력해야 하는 경우.
  • 허브가 멈추면 Plane·Gitea·Figma 작업까지 막히는 경우. 플러그인 훅은 허브가 없어도 작업을 막지 않습니다(fail-open, 실패해도 통과).

PRD 3작업 배경, 작업 환경, 지원 환경 범위

배경

v2 계획은 위키를 현황 화면으로 만들고, 작업 구조는 저장소 .ledger/plan/, 진행 상태는 포지 이슈에 두는 방식이었습니다. 이후 두 가지가 바뀌었습니다. 첫째, 별도로 설계하던 "기획자형 작업 계획서" 스킬을 이 플러그인에 합쳤습니다. 둘째, 사용자가 Plane을 도입해 역할을 나눴습니다(PMT D1–D4).

왜 상주 수집 서비스인가 D4

  • 세 도구 상태가 실시간으로 보이고, 팀이 같은 주소로 봅니다.
  • 받은 이벤트가 그대로 쌓여 로깅·추적 자료가 됩니다(구현 문서 4).
  • Figma는 View·Collab 좌석 토큰으로 파일을 조회하면 월 20회까지만 됩니다. 웹훅으로 받으면 이 한도를 피할 수 있습니다. 검증 [F2]

고르지 않은 안: A(명령을 실행할 때 HTML 생성)는 실시간이 아니고 팀 공유가 어렵습니다. C(엔진 하나로 A부터 시작)는 실시간이 뒤로 밀립니다. Plane 페이지나 Gitea 위키에 현황을 쓰는 방식은 사람이 고친 내용과 덮어쓰기가 충돌합니다. Plane API는 분당 60회로 제한됩니다 [P4].

도구별 수신 검증

도구검증 방식실패 시 도구 쪽 동작
Gitea웹훅 비밀값으로 본문을 HMAC-SHA256 서명한 X-Gitea-Signature 헤더를 확인합니다. 전달 ID는 X-Gitea-Delivery 검증 [G1]빠진 이벤트는 대조 작업이 보완합니다 제안
PlaneX-Plane-Signature(HMAC-SHA256)를 확인합니다. 전달 ID는 X-Plane-Delivery이고 재시도마다 새로 만들어집니다 검증 [P5]서버 오류·무응답이면 약 10분 기준 지수 대기로 재시도하고, 4xx는 재시도하지 않습니다. 5회 실패하면 웹훅을 끄고 만든 사람에게 메일을 보냅니다 검증 [P5]
Figma본문의 passcode가 등록 값과 같은지 확인합니다. 틀리면 400을 돌려주며, 이때 그 웹훅은 바로 멈춥니다 검증 [F3]5분·30분·3시간 뒤 3회 재시도 검증 [F3]
추론 허브는 서명 불일치에만 400을 돌려주고, 처리 실패는 200을 돌려준 뒤 안에서 재시도합니다. 근거: Plane은 5회 실패하면 웹훅을 끄므로, 허브 내부 오류가 도구 쪽 웹훅을 끄게 하면 안 됩니다. 전달 ID가 재시도마다 바뀌므로 중복 판정은 payload_sha256으로 합니다.

로그 형식

{"ts":"2026-12-02T09:14:03.120Z","level":"info","component":"receiver","source":"plane",
 "event_id":4182,"correlation_id":"pl-7f0c…","action":"stored","result":"ok","duration_ms":12}
  • 한 줄에 JSON 하나를 표준 출력으로 씁니다. Docker 로그가 모읍니다.
