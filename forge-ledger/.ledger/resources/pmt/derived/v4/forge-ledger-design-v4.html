forge-ledger 설계서 v4.2

Claude Code 플러그인 forge-ledger의 설계입니다. 플러그인은 두 부분으로 됩니다. 1부 작성방식은 작업 계획서(PRD 9항목과 구현 문서 9종)로 신규 착수, 기능 추가, 유지보수를 이끕니다. 2부 연결·대시보드는 Plane(작업·계획서), Gitea(코드·실제 문제), Penpot(화면, 자체 설치)을 잇고 정보를 모아 보여 주며 1부를 돕습니다.

이 문서도 그 작성방식으로 썼고, 플러그인에 예시로 들어갑니다. Part 1은 제품 요구사항 문서(PRD, Product Requirements Document), Part 2는 구현 문서 9종, Part 3은 플러그인에 넣을 작성방식 규격 원문입니다. 구현은 아직 하지 않습니다.

검증 공식 문서·서버에서 직접 확인 추론 근거를 밝힌 판단 제안 이 설계에서 정한 방식(작성자 판단) 결정 사용자가 정한 것(PMT 결정 번호)

하지 않을 것(비목표)

  • Plane이 이미 하는 작업 관리 기능을 다시 만들지 않습니다. 허브는 모으고 연결해서 보여 주기만 합니다.
  • 코드 리뷰 도구나 화면 설계 도구를 만들지 않습니다.
  • Plane 화면에서 사람이 직접 하는 일(cycle 닫기 등)은 막지 않습니다. 게이트는 플러그인 명령 경로에서만 막고, 그 밖의 경로는 허브가 알립니다(M10·M12).

실패로 보는 경우(반목표)

  • 대시보드가 원천이 되는 경우. 상태를 바꾸는 일은 각 도구에서 하고, 허브는 읽기 전용입니다.
  • 같은 내용을 사람이 두 도구에 두 번 입력해야 하는 경우.
  • 허브가 멈추면 Plane·Gitea·Penpot 작업까지 막히는 경우. 플러그인 훅은 허브가 없어도 작업을 막지 않습니다(fail-open, 실패해도 통과).
  • 계획서 작성이 코드 수정보다 무거워 급한 수정을 미루게 되는 경우. 수정 흐름(plan fix)은 문서 작성을 요구하지 않습니다.
  • "해당 없음"만으로 형식 검사를 통과하는 경우. 해당 없음에는 이유가 필수이고, 독립 검토가 그 이유를 읽습니다.

PRD 3작업 배경, 작업 환경, 지원 환경 범위

배경

v2 계획은 위키를 현황 화면으로 만들고, 작업 구조는 저장소 .ledger/plan/, 진행 상태는 포지 이슈에 두는 방식이었습니다. v3에서는 별도로 설계하던 "기획자형 작업 계획서" 스킬을 합치고, Plane을 도입해 역할을 나눴습니다(PMT D1–D4). 다만 v3는 Plane·대시보드가 중심이었고, 작성방식은 플러그인 구성 표의 몇 줄에 그쳤습니다.

v3 검토에서 사용자가 두 가지를 바로잡았습니다. 첫째, 저장소 하나에 Plane 프로젝트가 여러 개 붙습니다(D5). 둘째, 작성방식 자체가 프로젝트를 이끄는 플러그인 기능이어야 합니다(D6). 이끄는 강도는 혼합으로 정했습니다(D7). v4는 이 세 결정을 반영해 작성방식을 1부, 연결·대시보드를 2부로 다시 짰습니다.

v4를 쓰는 동안 사용자가 미결 질문에 답했습니다(PMT D8–D13). Telegram 알림을 더하고, 위키 갱신을 다시 범위에 넣고, 엔터티를 3년 보관하고, 플러그인 저장소를 내부 http·외부 https로 여는 로컬 Gitea에 두고, 구현 문서에 인증·보안을 더합니다. 이어서 화면 도구는 무료로 자체 설치하는 Penpot으로 정했습니다(D14). 기능 규모는 플러그인이 판단해 추천하고 사용자가 고르며, 넘어가면 "<저장소명> 유지보수" 프로젝트에 임시로 넣습니다(D15). Telegram은 지정한 봇 1개에만 보냅니다(D17).

PlaneX-Plane-Signature(HMAC-SHA256)를 확인합니다. 전달 ID는 X-Plane-Delivery이고 재시도마다 새로 만들어집니다 검증 [P5]서버 오류·무응답이면 약 10분 기준 지수 대기로 재시도하고, 4xx는 재시도하지 않습니다. 5회 실패하면 웹훅을 끄고 만든 사람에게 메일을 보냅니다 검증 [P5]
Penpot웹훅은 팀 단위로 등록한 URL에 POST되고, 문서에 서명 방식이 없습니다 검증 [N1]. 허브는 등록 URL에 비밀 경로 값을 넣고 사내망에서만 받으며, 본문은 변경 알림으로만 쓰고 내용은 RPC API로 다시 읽습니다 제안빠진 이벤트는 대조 작업이 보완합니다
추론 허브는 서명 불일치에만 400을 돌려주고, 처리 실패는 200을 돌려준 뒤 안에서 재시도합니다. 근거: Plane은 5회 실패하면 웹훅을 끄므로, 허브 내부 오류가 도구 쪽 웹훅을 끄게 하면 안 됩니다. 전달 ID가 재시도마다 바뀌므로 중복 판정은 payload_sha256으로 합니다.
