# 작업 일지(work log) 설계

- 작성일: 2026-11-26
- 상태: 승인(2026-11-26, 사용자가 구현 계획 작성을 요청)
- 구현 계획: `../plans/2026-11-26-worklog.md` (PMT 이전 계획에 이어 Task 11~16)
- 앞선 설계: `2026-11-25-hub-skeleton-design.md`(D22~D29), `2026-11-26-pmt-migration-design.md`(D30~D36)

## 1. 목적과 이유

날짜별로 "누가 어디서 무엇을 했는지"를 남기고 모아 본다. 쓰임새는 둘이다.

1. 한 사람이 여러 PC·서버에서 한 일을 한곳에서 날짜별로 확인한다.
2. 팀에 배포한 뒤 팀원이 서로의 작업을 확인한다.

Plane 작업 항목에 묶이지 않은 일(서버 점검, 조사, 다른 저장소 작업)도 남긴다. 그래서 기록 단위는 저장소가 아니라 사람이다. 저장소에 묶인 `.ledger/`에는 두지 않는다.

## 3. 목표 · 비목표 · 반목표

목표
- 두 컴퓨터에서 쓴 기록이 동기화 뒤 어느 쪽에서든 `ledger log show`에 함께 나온다.
- 다른 팀원이 자기 토큰으로 내 기록을 조회한다.
- Plane에 연결되지 않아도 기록이 로컬에 남고, 연결되면 중복 없이 올라간다.
- 허브 수집이 작업 일지를 모으고, 조회 API로 날짜·사람별로 돌려준다.

비목표
- 허브 대시보드 화면. 전면 재작성(B11)에서 이 API를 써서 만든다.
- ksadmin-works 업무보고로 내보내기. 필요하면 나중에 따로 한다.
- CLI로 기록을 고치거나 지우기. Plane 화면에서 한다.
- 작업 시간 집계(시간 추적).
- Linear·GitHub·GitLab 어댑터. 연결 규격만 둔다(D25).

반목표 (기술적으로 돌아가도 실패로 본다)
- 민감값(주소·토큰·홈 경로 등)이 든 기록이 Plane에 올라간다. 팀원 모두가 보기 때문이다.
- 다시 동기화할 때 같은 기록이 두 번 올라간다.
- Stop 훅이 세션 종료를 끝없이 막거나, Plane이 멈췄다는 이유로 막는다.
- 허브가 작업 일지의 원천이 된다. 허브 DB를 지워도 기록은 Plane에 남아야 한다.

## 4. 접근 방식

| 방식 | 내용 | 결과 |
|---|---|---|
| A | 허브에 쓰기 API를 열고 허브 DB를 원천으로 둔다 | 미채택. 허브 읽기 전용 원칙과 NFR-06(허브 DB를 지워도 대조로 복구)을 바꿔야 하고, 허브 컨테이너·개인 계정·백업이 먼저 필요하다. 허브는 아직 골격뿐이다 |
| B | Plane에 저장하고 `ledger log show`로만 본다 | 미채택. 통합 화면 요구(리모트에서 보기)를 채우지 못한다 |
| C (선택) | B + 허브가 Plane 기록을 모아 날짜·사람별로 보여 준다 | 원칙을 지키면서 지금 쓰기 시작하고, 허브가 서면 통합 화면이 생긴다 |
| 기록 전용 git 저장소 | 사람별·날짜별 파일을 push | 미채택. 기록마다 자동 push가 필요해 "push는 요청 때만" 규칙과 부딪히고, 같은 날 여러 기계가 쓰면 충돌한다 |

## 5. 구성

### 5.1 Plane 구조

- 워크스페이스에 팀 공용 프로젝트 "작업 일지" 하나를 둔다. 키는 userConfig `worklog_project_key`(기본 `WLOG`)다.
- 사람마다 달마다 작업 항목 하나를 둔다. 이름은 `<Plane 표시 이름> YYYY-MM`이다. 댓글이 한 항목에 끝없이 쌓이지 않게 하고, 허브가 최근 두 달 항목만 읽게 하기 위함이다 [설계 판단].
  - 표시 이름은 `GET /api/v1/users/me/`의 `display_name`이다(`UserLiteSerializer` 필드). 지금 `whoami()`가 돌려주는 이메일은 노출 검사 패턴에 걸리므로 쓰지 않는다.
- 기록 한 건은 댓글 하나다. 작성자는 토큰 주인으로 저장된다(`plane-api-1` 컨테이너 `/code/plane/api/views/issue.py:1588`, `serializer.save(..., actor=request.user)`).
- 댓글 첫 줄: `[일지] <ISO 시각> <호스트 라벨> <auto|manual>`. 저장소 이름과 항목 코드는 있을 때만 같은 줄 뒤에 `repo=<이름>`, `item=<코드>`로 붙인다. 둘째 줄부터 본문이다.
- 중복 방지는 Plane의 원천 표식을 쓴다. 항목과 댓글 모두 `external_source=forge-ledger-worklog`를 달고, `external_id`는 항목이 `<사용자 id>/<YYYY-MM>`, 댓글이 기록 ID다. 같은 표식으로 다시 만들면 Plane이 HTTP 409와 기존 `id`를 돌려준다(같은 파일 항목 생성 534~575줄, 댓글 생성 1551~1587줄). 그래서 올리는 도중 끊겨도 다시 올리면 중복이 생기지 않는다.
- 항목 주인(`external_id`의 사용자 id)과 댓글 작성자(`actor`)가 다른 댓글은 일지로 읽지 않는다. 남의 일지에 끼워 쓰는 것을 막기 위함이다 [설계 판단].
- `ledger log init`: "작업 일지" 프로젝트가 없으면 만든다. 이미 있으면 아무것도 하지 않는다. 팀원을 프로젝트 구성원으로 넣는 일은 Plane 관리자가 화면에서 한다.
- 시각은 기록한 컴퓨터의 현지 시각을 오프셋과 함께 적는다. 날짜 구분도 그 시각을 따른다. 나중에 올려도 첫 줄의 원래 시각을 쓴다(댓글 생성 시각이 아님).

### 5.2 로컬 저장

- 위치: 상태 폴더(`default_state_dir`, `FORGE_LEDGER_STATE_DIR` → `$XDG_STATE_HOME/forge-ledger` → `~/.local/state/forge-ledger`) 아래 `worklog/`. 폴더 권한 0700, 파일 0600.
- `worklog/<YYYY-MM>.jsonl`: 기록마다 한 줄. 필드는 `id`(uuid4 hex), `at`, `host`, `source`(auto|manual), `text`, `workspace`(쓸 때의 Plane 워크스페이스 이름), `repo`(선택), `item`(선택), `session`(자동 기록의 세션 ID, 선택).
- 미전송 기록은 쓸 때의 `workspace`로만 올린다. 지금 설정된 워크스페이스와 다르면 올리지 않고 "다른 워크스페이스 기록 N건 미전송"으로 알린다. 작성자는 올릴 때의 토큰 주인이 된다. 한 컴퓨터는 한 사람이 쓴다고 본다 [설계 판단].
- `worklog/sent.json`: 올린 기록 ID → Plane 댓글 ID.
- 같은 컴퓨터의 여러 세션이 동시에 쓰므로 잠금 파일(`fcntl`, `ratelimit.py` 방식)을 쓴다.
- 로컬 파일은 지우지 않는다. 보관 기간 정리는 비목표다.

### 5.3 쓰기 규칙 (두 경로 공통)

- `ledger log add "<내용>" [--item FL-12] [--repo <이름>] [--at <ISO 시각>] [--auto]`
- 본문 400자 이하, 여러 줄 가능. 빈 본문은 거부한다.
- 쓰기 전에 노출 검사(`secrets.find_exposures`, 이전 설계 10절)를 통과해야 한다. 걸리면 로컬에도 쓰지 않고 패턴 이름만 알린다. 값은 출력하지 않는다.
- 로컬에 먼저 쓰고, 이어서 바로 올려 본다. 토큰이 없거나 Plane이 응답하지 않으면 "미전송"으로 두고 종료 코드 0으로 끝낸다.
- `--repo` 기본값은 현재 폴더가 git 저장소일 때 그 저장소 이름, 아니면 비움.
- 호스트 라벨: userConfig `worklog_host_label`. 비어 있으면 `socket.gethostname()`의 첫 마디. 라벨도 노출 검사를 거친다.
- 항목 코드가 있어도 그 항목에 댓글을 따로 달지 않는다. 항목의 인계는 `ledger work note`가 맡는다 [설계 판단].

### 5.4 자동 경로 (Stop 훅)

- 새 훅 `hooks/stop.py`. userConfig `worklog_auto`(기본 true)가 false면 아무것도 하지 않는다.
- 막는 조건: 이번 세션에서 마지막 작업 일지 기록 뒤에 도구 사용이 있었고, 이번 세션의 마지막 기록이 없거나 60분보다 오래됨. 판정은 훅 입력의 `session_id`와 `transcript_path`, 로컬 `worklog/`의 `session` 필드로 한다 [판정 세부는 빌더 몫].
- 막을 때는 종료 코드 2와 함께 지시문을 낸다: "이번 세션에서 한 일을 1~3줄로 `ledger log add --auto`에 남긴 뒤 종료하라".
- 막지 않는 경우: 입력의 `stop_hook_active`가 true(무한 반복 방지), 상태 폴더를 쓸 수 없음, 그 밖의 모든 오류(fail-open).
- Plane 연결은 판정에 쓰지 않는다. 로컬 기록만 있으면 통과한다.

### 5.5 동기화와 조회

- `ledger log sync`: 미전송 기록을 시각순으로 올린다. 이미 같은 표식의 댓글이 있으면 `sent.json`만 채운다. 달마다 항목이 없으면 만든다. Plane 호출은 기존 공유 제한기(분당 50회)를 쓴다.
- 동기화 시점: `log add` 직후 한 번, SessionStart(분리된 백그라운드, 잠금으로 중복 방지), 사용자가 직접 실행할 때.
- `ledger log show [--date YYYY-MM-DD | --from … --to …] [--user <표시 이름> | --all]`: 기본은 오늘, 나. Plane에서 읽어 시각순으로 출력한다. 범위 제한은 없다(Plane을 직접 읽으므로).
  - 조회 대상에 내가 포함되면, 이 컴퓨터의 미전송 기록을 `(미전송)` 표시와 함께 섞어 보여 준다. 기록 ID로 중복을 없앤다 [설계 판단].
  - Plane에 닿지 않으면 로컬 기록만 보여 주고 그 사실을 한 줄로 알린다.
- SessionStart 요약에 미전송 건수가 있으면 한 줄을 더한다. 전체 상한 1,500자는 그대로다.

### 5.6 허브 수집과 조회 API

- `hubsync`에 종류 `worklog`를 더한다. "작업 일지" 프로젝트 항목의 댓글을 읽어 `(source_id, 'worklog', <기록 ID>)`로 upsert한다.
- 수집 범위 [설계 판단]:
  - 주기 대조(10분)는 이번 달과 지난달 항목만 읽는다.
  - 첫 수집과 하루 한 번은 모든 달 항목을 읽는다. 늦게 올라온 오래된 기록과 오래된 달의 수정·삭제는 이 전체 수집에서 반영된다.
  - 읽은 범위 안에서 Plane에 없는 기록은 `state='deleted'`로 바꾸고 API에서 뺀다. 읽지 않은 범위의 행은 건드리지 않는다(허브 골격 설계 6.3절 4번과 같은 방식).
  - 댓글 수정은 upsert로 반영한다.
- attrs: `at`, `author`(Plane 표시 이름), `host`, `source`, `repo`, `item`, `text`.
- 이 프로젝트는 저장소에 묶이지 않는다. `entity.repo_id`·`sync_run.repo_id`가 `NOT NULL`이므로(`ledger/hubstore.py` 스키마) 워크스페이스 단위 행은 `repo_id = 0`으로 둔다. 스키마 버전은 바꾸지 않는다. 등록 저장소가 없어도 Plane 토큰과 워크스페이스가 있으면 수집한다 [설계 판단].
- API: `GET /api/v1/worklog?from=YYYY-MM-DD&to=YYYY-MM-DD[&user=<표시 이름>]`. 기존 접속 토큰 보호와 응답 헤더를 그대로 쓴다. 범위는 최대 62일.
- 화면은 B11에서 이 API로 만든다(비목표).

### 5.7 연결 규격

`adapters.py`에 `WorklogStore` Protocol을 더한다: `ensure_project()`, `ensure_month_item(user, month)`, `list_entries(from_, to, user=None)`, `post_entry(entry)`. Plane이 구현한다. 다른 PM 도구는 이 규격만 지키면 된다(D25).

## 6. 제약

- 민감값은 계획·코드·테스트·기록에 넣지 않는다.
- Python 표준 라이브러리만 쓴다. 3.10~3.13 매트릭스와 CI 검사 7개를 통과해야 한다.
- push·배포는 사용자가 요청할 때만 한다.
- 선행 작업: PMT 이전 계획의 Task 1(노출 패턴 확장)과 Task 3(Plane 댓글·라벨 쓰기)은 끝났다(커밋 `8b202e9`, `8621ada`). 다만 `cli.py`·`plane.py`·`session_start.py`를 이전 계획 Task 5~9도 고치므로, 작업 일지 구현은 이전 계획 Task 9가 끝난 뒤 시작한다.

## 7. 성공 확인

1. 상태 폴더 둘(두 컴퓨터 흉내)에서 연결 없이 기록을 쓰고 동기화하면, 어느 쪽의 `log show --date`에도 두 기록이 모두 나온다. 두 번째 동기화에서 새로 올리는 것은 0건이다.
2. 다른 Plane 사용자 토큰으로 `log show --user <나>`를 실행하면 내 기록이 나온다(실서버).
3. 홈 경로가 든 기록은 거부되고, 로컬 파일과 Plane 어디에도 남지 않는다. 출력에 값이 없다.
4. Stop 훅: 도구 사용이 있고 기록이 없는 세션은 종료 코드 2, `stop_hook_active`면 0, Plane이 멈춰도 로컬 기록 뒤에는 0이다.
5. `ledger sync` 뒤 `/api/v1/worklog` 건수가 같은 범위의 Plane 댓글 수와 같다.
6. `bash ci/run-checks.sh all` 통과.

## 8. 검토 후 정한 것 (설계 판단, 사용자 확인 대상)

- 사람마다 달마다 항목 하나(5.1).
- 자동 기록 간격 60분, 판정은 도구 사용 여부(5.4).
- 항목 코드가 있어도 항목 댓글을 따로 달지 않는다(5.3).
- 허브 화면은 B11로 미루고 이번에는 수집과 API까지(5.6).
- 노출 검사에 걸린 기록은 로컬에도 쓰지 않는다(5.3).
- 미전송 기록은 쓸 때의 워크스페이스로만 올리고, 작성자는 올릴 때의 토큰 주인이다(5.2).
- `log show`는 내 미전송 기록을 `(미전송)`으로 섞어 보여 준다(5.5).
- 허브는 10분마다 최근 두 달, 첫 수집과 하루 한 번은 전체를 읽고, 읽은 범위에서 사라진 기록을 삭제로 반영한다(5.6).
